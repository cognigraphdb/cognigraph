# CG-143: Tenant suspend and delete hold the global admission lock while a model-bound job step finishes

- Status: Open
- Priority: P2
- Area: Server / jobs; tenant lifecycle (Enterprise)
- Found: 2026-11-11
- Verification: Pending (source-confirmed in the 2026-11-11 review; not executed)

## Problem and evidence

The tenant `update` and `remove` handlers take `state.tenant_lifecycle_lock`
and then await `jobs.pause_tenant()`, which polls until the tenant's running
step ends, with no timeout (`routes/tenants.rs:121-145`, `:250-265`,
`jobs/tenant_lifecycle.rs:6-32`). Every authenticated request takes the same
lock in `admit` (`auth_middleware.rs:67`).

The draft and side-view loops check pause, cancel and shutdown only at batch
boundaries (`jobs/worker.rs:355-422`, `:547-568`). The batch is
`COGNIGRAPH_JOB_INGEST_BATCH_SIZE` (default 25), frozen into the job payload.
One draft step is therefore up to 50 sequential completions and one side-view
step up to 25 completion and embedding pairs, each bounded only by the
120-second client timeout. Durations are from the code path, not measured.

Consequences:

- A host admin suspends or deletes tenant A mid-batch. Requests for all
  tenants queue in the auth middleware until the step ends or the request
  timeout drops them.
- Cancellation and graceful shutdown wait for the same batch.
- A mid-batch error or crash loses up to two batches of paid completions.
- Raising the ingest batch size for throughput enlarges the model-bound step.

## Acceptance

- [ ] Tenant lifecycle handlers do not hold the admission lock while waiting for a worker, and the drain is bounded.
- [ ] Model-bound job kinds checkpoint and observe cancel, pause and shutdown per document, or have their own batch setting.
- [ ] `docs/operations/jobs.md` states the cancellation and fairness granularity of draft and side-view jobs.
