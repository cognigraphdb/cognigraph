# CG-35: Native collection ensures invalidate derivatives on unchanged startup

- Status: Resolved
- Priority: P2
- Area: Native startup / derivative reuse
- Found: 2026-09-09
- Reviewed revision: `fb49c78` and the CG-34 working tree
- Verification: Pre-fix Native/release reproduction, corrected Rust gates and authenticated release restarts
- Resolved: 2026-09-09 (committed locally as `d98e374`)

## Problem

Before this fix, Native `ensure_collection` persisted a `PutCollection` even when the collection
already exists with the same type. Every such call advances the global data
generation and revision. Auth initialization ensures its three existing
collections on startup, invalidating an otherwise current vector sidecar.
The next search scans redb and rebuilds the file instead of reusing it.

This is unnecessary startup and first-query work, especially for large stores;
the observed rebuild preserves search data. It also makes whole-server restarts
behave differently from direct NativeBackend warm-open tests, where no schema
initialization writes occur and the current file is reused.

## Evidence

- `crates/cognigraph-native/src/memory/backend.rs:230-246` always persists the
  collection ensure, including an existing collection with its recorded type.
- `crates/cognigraph-native/src/storage.rs:396-422` advances generation and
  assigns a new revision for the transaction before applying `PutCollection`.
- `crates/cognigraph-auth/src/lib.rs:217-226` ensures three collections during
  initialization; the server calls it at startup.
- The [CG-34 baseline HTTP evidence](evidence/sidecar-model-filter-baseline-http-2026-09-09.json)
  records different sidecar file hashes and generations after each authenticated
  server restart, but identical vector-payload hashes. The behavior also occurs
  with the corrected CG-34 binary; model pre-filtering does not address it.

## Acceptance criteria

- [x] Make an already-satisfied collection ensure a true no-op without changing
  existing collection-type behavior or concurrent creation correctness.
- [x] Preserve generation/revision and reusable derivatives on no-op ensures;
  actual collection creation must still advance the revision.
- [x] Verify authenticated release-server restart reuse with the same rows and
  vector files, alongside the Rust gates and concurrent ensure coverage.

## Resolution

An existence check under the creation write lock now returns before persistence
for existing collections. Their original type, data, process write version,
generation, and revision remain unchanged. Sixteen concurrent ensures commit
one creation; actual creation and drop/recreation still advance versions.

All 61 Native tests, formatting, strict Clippy, and 958 reported workspace
tests passed; eight unconfigured Arango entries early-returned. The release
matrix passed 112 checks across nine authenticated restarts in all three
persistent Native configurations, including stores seeded by the old release.
It preserved 18 derivatives unnecessarily rewritten by the baseline and
retained seven required rebuilds after real changes. Vector warm loading still
reconstructs key/model metadata from redb; no startup timing improvement is
claimed. See the [verification report and evidence](collection-ensure-2026-09-09.md).
