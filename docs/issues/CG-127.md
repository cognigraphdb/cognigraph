# CG-127: VECTOR_SEARCH pushes LIMIT down as top-K before filters, sorts and grouping

- Status: Open
- Priority: P2
- Area: CGQL / pushdown
- Found: 2026-11-11
- Verification: Pending (source-confirmed in the 2026-11-11 review; not executed)

## Problem and evidence

`crates/cognigraph-query/src/executor/materialize.rs:506-520` computes the
backend top-K as `plan.limit … map_or(100, fetch_len)`. It ignores residual
FILTERs, SORT, COLLECT and later FORs, unlike the guarded scan pushdown at
`:81-92`. Without a LIMIT the backend silently returns 100 hits while EXPLAIN
shows `limit_pushdown: null`; the in-memory engine returns every row
(`:665-688`), so the two engines diverge. The default of 100 is not in
`docs/reference/cgql.md:871-873`.

Failure cases:

- `FOR d IN VECTOR_SEARCH(docs, @v) FILTER d.lang == "de" LIMIT 10 RETURN d`
  filters only the 10 nearest and can return nothing while matches exist.
- `… COLLECT c = d.category WITH COUNT INTO n LIMIT 3 …` groups over 3 hits,
  although LIMIT applies to groups.
- `… SORT d.created DESC LIMIT 5` sorts only the 5 nearest.

No test combines VECTOR_SEARCH with a residual FILTER, SORT or COLLECT plus
LIMIT.

## Acceptance

- [ ] LIMIT becomes K only under the same conditions as scan LIMIT pushdown.
- [ ] The default K is explicit, documented and shown by EXPLAIN.
- [ ] Dual-engine corpus cases cover FILTER, SORT and COLLECT with LIMIT.
