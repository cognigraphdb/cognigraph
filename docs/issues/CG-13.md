# CG-13: Side-view orphan prevention is bypassed by alternate deletes

- Status: Resolved
- Resolved: 2026-09-09
- Priority: P2
- Area: Generated retrieval data
- Found: 2026-09-08
- Reviewed revision: `bc4bff1` (workspace 2.6.0)
- Verification: Pre-fix release reproduction, 922 passing Rust tests, injected failures, and release HTTP across all three persistent Native modes

## Problem

Side-view cleanup exists only in the direct document DELETE handler and ignores cleanup failures. Batch/CGQL/Lua deletes and collection drops bypass it. The generation job also writes after provider calls without checking that its source still exists, so deletion racing generation can recreate orphaned retrieval surfaces. Staleness after an ordinary parent update is an explicitly accepted product limitation, with manual regeneration, and is outside this issue.

## Evidence

- `crates/cognigraph-server/src/routes/documents.rs:19-60,143-183` — best-effort DELETE-only cascade.
- `crates/cognigraph-server/src/routes/batch.rs:26-37` — direct generic batch.
- `crates/cognigraph-server/src/jobs.rs:3200-3299` — source read, provider awaits, then independent side-view write.
- `docs/decisions/decision_sideviews_provider_and_benchmark.md:153-160` — parent updates intentionally require manual regeneration.

## Reproduction / failure sequence

In a disposable store, import one ordinary generated side-view pointing to `notes/a`, then delete `notes/a` through `/api/batch`. The deletion returned HTTP 200; listing `side_views` still returned the row and its old question/answer. Separately, the source sequence permits a parent deletion between generation's read and final batch.

## Acceptance criteria

- [x] Enforce cascade rules at a shared boundary covering parent deletes and collection drops.
- [x] Fence publication atomically against parent deletion so generation cannot reinsert orphaned rows.
- [x] Make cleanup failure visible or recoverable and test delete/drop versus generation, retry, and regeneration.

Run the repository Rust gates and a focused runtime regression before closing this issue. See [review evidence](review-2026-09-08.md).

## Resolution

The server's shared side-view lifecycle now covers direct HTTP, batch, CGQL,
Lua delete/batch/query, and collection drop. Native document deletion commits
source and derivative removals atomically; batch output order/count and the
DELETE count envelope are preserved. Collection drops clean up derivatives first
and propagate failures, with retry semantics for partial progress.

Generation captures a revocable source token scoped to the tenant incarnation.
Provider calls run outside the lock; publication validates the token and source
under the same lock as deletion and holds it through the atomic write. A
same-key recreation does not revive a stale token. Failed publication reports a
source conflict; retry reads the current source or skips one that is absent.
Regeneration replaces the current rows atomically, and overlapping default
publication remains idempotent.

The final release regression passed 21 deletion cases, 42 controlled provider
races and retries, six source-identity rejections, regeneration/provider-failure
and batch rollback cases, and three persistent restarts. Formatting, strict
Clippy, and all 922 Rust tests passed. See the
[full report, compatibility limits, and corrected test attempts](side-view-lifecycle-2026-09-09.md)
and [decision](../decisions/decision_sideviews_provider_and_benchmark.md#shared-deletion-and-publication-contract-cg-13-2026-09-09).

CG-13 temporarily required NFC source handles. [CG-33](CG-33.md) subsequently
removed that restriction by preserving exact opaque references and job payloads;
collection names still cannot contain `/`. Existing malformed references require
explicit diagnosis/repair; see the [current contract](../decisions/decision_exact_reference_identity.md).
