# CG-101: Hybrid search sums chunk ranks per parent, so the vector leg can outvote BM25

- Status: Open
- Priority: P3
- Area: Search / hybrid
- Found: 2026-09-23
- Verification: Pending (source-confirmed; symptoms measured in CG-98)
- Scheduling: Design question for the owner; measure before changing the default

## Problem and evidence

`POST /api/search/hybrid` (`crates/cognigraph-server/src/routes/search/hybrid.rs`)
fuses its legs with reciprocal rank fusion (RRF). Chunk rows carry a
`document_id` pointing at their parent, and the fusion loop adds
`vector_weight / (rrf_k + rank + 1)` to the parent for every chunk hit in
the vector leg's `limit × 3` candidates. A parent with several matching
chunks therefore collects several vector contributions, while the BM25 leg
contributes at most one per parent. The side-view leg behaves the same way.

The [CG-98](CG-98.md) benchmark shows the symptoms on English queries
(MRR@10, 100 queries, 200 DailyMed labels, equal weights):

| Embedder | BM25 alone | Vector alone | Hybrid |
|---|---|---|---|
| BGE-M3 | 0.667 | 0.535 | 0.553 |
| OpenAI text-embedding-3-small | 0.667 | 0.654 | 0.670 |
| Gemini gemini-embedding-2 | 0.667 | 0.848 | 0.848 |

With a weak embedder, hybrid search scores below BM25 alone. With a strong
one, BM25 adds nothing measurable. Both are consistent with the vector leg
dominating through repeated chunk contributions, but this has not been
isolated yet.

## Acceptance

- [ ] The CG-98 benchmark is extended with a collapse variant (maximum or
      first rank per parent per leg) and run on the frozen inputs, with
      paired intervals against the current sum.
- [ ] The owner decides the default from that measurement, and the decision
      is recorded. Any change keeps the current behavior reachable for
      comparison.
