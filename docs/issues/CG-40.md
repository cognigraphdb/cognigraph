# CG-40: Directed completion schema leaves request-bound identifiers unconstrained

- Status: Resolved
- Priority: P2
- Area: Directed construction / completion contract
- Found: 2026-09-09
- Reviewed revision: `b9a97f9`
- Verification: Five invalid chunk citations captured from Luna; release HTTP/schema reproduction

## Problem

The strict completion schema requires `chunk_id` and `relation` to be strings
but does not constrain them to the IDs and relation names in the request. A
schema-valid response can therefore invent or decorate an identifier, causing
otherwise parseable proposals to be rejected downstream.

The gates correctly reject unknown identifiers. The gap is the avoidable
provider contract mismatch, not a request to repair identifiers heuristically
or weaken the rejection behavior.

## Evidence

- `crates/cognigraph-construct/src/directed.rs:315` — `proposal_schema` has no
  request inputs; `relation` and `chunk_id` are unconstrained strings.
- The [document trial captures](../evidence/research-luna-documents-2026-09-09.md#artifact-b4aa040d779fc3e3672c)
  contain five proposals across two documents whose cited ID is
  `chunk development-...` instead of the supplied `development-...`.
- The real server returned HTTP 200 with those proposals in `skips` and no
  stored facts for the two affected documents. No automatic ID repair occurred.
- The [minimal release reproduction](../evidence/engineering-historical-checks.md#artifact-b1e02c24a04ed025346b)
  captures the schema's `chunk_id: {"type":"string"}` and shows
  `chunk source-1` rejected for a request containing only `source-1`.

## Acceptance criteria

- [x] Derive the response schema from the validated request, using enums for
  allowed chunk IDs and taxonomy relation names while retaining strict mode.
- [x] Keep local identifier validation and unknown-ID rejection authoritative
  when a provider ignores or does not fully enforce the schema.
- [x] Do not trim, prefix-strip, fuzzy-match or infer replacement identifiers.
- [x] Cover multiple chunks, opaque/Unicode IDs, exact relation identity, and
  malformed provider output without changing valid-empty replacement semantics.
- [x] Verify captured OpenAI/Gemini request schemas, Rust gates, and focused
  release HTTP behavior, then measure the change on development data only.

Identifier binding will not recover missing facts, fix wrong semantics, or
qualify the model as a judge. The original experiment and its versioned scoring
correction must remain immutable; the holdout must remain unrun during fixes.

## Resolution — 2026-09-09

`proposal_schema(taxonomy, chunks)` now supplies exact, sorted string enums for
both fields, while retaining the closed, fully required schema and strict OpenAI
mode. Opaque Unicode IDs and exact relation names are neither normalized nor
repaired. Local lookup still rejects a provider's invalid identifiers. The
[contract decision](../decisions/decision_directed_extraction_contracts.md)
records policy v2 and unchanged malformed/empty response semantics.

Formatting, strict Clippy, all 967 reported Rust tests, the release build and
[34 OpenAI/Gemini HTTP cases](../evidence/engineering-historical-checks.md#artifact-97932bee025d16118de5)
passed. Eight Arango test entries returned early without the exported password;
live verification here uses disposable Native databases.

The [separately frozen development candidate](../research/experiments/luna-directed-v2-2026-09-09/results.md)
completed 40 real Luna-low calls with zero invalid chunk citations, versus five
in the baseline, and zero invalid relation names. It stored 35 occurrences with
20 published-reference matches, versus 32/16 previously, at an estimated
$0.0194147 token cost. All request prompts remained identical; only the two
schema enums changed. One generation pass cannot establish an accuracy gain
caused by the schema alone. The original source/labels/captures and the unrun
80-document holdout remain unchanged; reference and negative-case qualification
is still pending.
