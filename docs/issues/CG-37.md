# CG-37: Nested lifted subqueries can reuse a synthetic binding name

- Status: Resolved
- Priority: P2
- Area: CGQL parser / nested scope
- Found: 2026-09-09 while verifying CG-28
- Reviewed revision: `9fb4933` (workspace 2.6.0)
- Verification: Baseline corpus/release reproduction; corrected Rust gates and release HTTP/Lua checks
- Resolved: 2026-09-09 (committed locally as `c48a3b4`)

## Problem

Before this fix, `desugar_subqueries` reset its synthetic-name counter for each nested query.
A prior lifted expression can already bind `$sq0` in the outer scope when a
nested expression tries to bind its own `$sq0`. Validation forbids shadowing,
so otherwise valid queries fail with `variable $sq0 is declared more than once`.
The `$` prefix prevents collisions with user variables but not other generated
bindings visible through correlation.

## Reproduction

Using the shared query corpus (four `documents`):

```cgql
LET n = LENGTH((FOR d IN documents RETURN d._key))
RETURN {n, nested: (FOR x IN [1] RETURN LENGTH((FOR d IN documents RETURN d._key)))}
```

Expected: `[{"n":4,"nested":[4]}]`. Before the fix, planning failed with the duplicate
binding error, before execution. The same nested expression without the earlier
lifted `LET` succeeds. This is not the intentional four-level nesting limit.

## Evidence

- [Parser](../../crates/cognigraph-query/src/parser/mod.rs): `desugar_subqueries`
  previously created a new counter per query, and `hoist_expr` recursively
  desugars each inner query before allocating the enclosing synthetic binding.
- [Validator](../../crates/cognigraph-query/src/validation.rs): nested validation
  clones the enclosing scope and rejects duplicate variable names.
- [Regression corpus case](../../crates/cognigraph-query/tests/corpus/exec/sq_nested_binding_collision.cgql)
  now requires the correct rows; the [standalone nested case](../../crates/cognigraph-query/tests/corpus/exec/sq_expr_nested.cgql)
  retains the supported control.
- [CG-28 verification](subquery-contract-2026-09-09.md) covers the release HTTP/Lua
  result as a known defect, not as an intended language exclusion.

## Acceptance criteria

- Allocate generated names without collisions across visible nested scopes,
  preserving user-variable shadowing rejection and ordinary correlation.
- Move this known-failure corpus case into `exec` with the expected result;
  cover multiple nested/sibling lifted expressions and explicit LET subqueries.
- Preserve binding collection, depth limits, parse errors, mutation restrictions,
  budgets, and execution/analysis agreement.
- Run all Rust gates and focused release HTTP/Lua checks before closure. Update
  CG-28's specification caveat when the defect is fixed.

## Resolution

One counter now spans the entire parsed query, including explicit LET subquery
bodies and lifted nested expressions. It resets for each parse and preserves
user-variable shadowing rejection. The original reproducer moved from the
validation-error corpus to execution, alongside four further nested, sibling,
correlated, bind-variable, and DOCUMENT cases. Tests cover binding collection,
repeatable parsing, depth limits, dynamic analysis, and source-row budgets.

Formatting, strict Clippy, and all 953 reported Rust tests passed; eight
unconfigured Arango entries early-returned. The saved release reproduced 40
name collisions across five shapes. The corrected release returned the expected
results through HTTP/Lua and analysis in resident/paged Native stores. Its 180
observations include four known CG-38 status mismatches, subsequently resolved
with [separate verification](query-error-status-2026-09-09.md).
See the [verification report and evidence](subquery-bindings-2026-09-09.md).
