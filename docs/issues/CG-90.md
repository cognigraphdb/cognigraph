# CG-90: Construction gate refusals are not durably recorded

- Status: Resolved
- Priority: P2
- Area: Construct / directed
- Found: 2026-09-22
- Verification: Construct, ledger and route tests on the Enterprise build, Community clippy, docs and registry gates, full local gate before the local develop merge on 2026-09-22
- Resolved: 2026-09-22

## Problem and evidence

Refusing an unsupported fact is the product's central governance claim, and the
gate 3 baseline ([decision](../decisions/decision_gate3_baseline.md)) reports
the count of narrative candidates quarantined rather than asserted. At 2.7.15
the runtime does not keep an equivalent record for the request-time gates:

- `POST /api/construct/directed`
  (`crates/cognigraph-server/src/routes/construct/directed.rs`) returns
  `outcome.skips` in the HTTP response body only. The six gates in
  `gate_directed_proposals` (`crates/cognigraph-construct/src/directed.rs`)
  — relation in taxonomy, chunk in request, usable endpoints, verbatim quote,
  endpoints in the evidence window, affirmed `require_in_sentence` phrase —
  each produce a skip string that is discarded once the response is sent.
- `POST /api/construct/propose` returns `skipped[]` (paraphrased triggers,
  no candidate chunks) the same way.
- The only persisted refusal-adjacent artifact is the `fact_semantics`
  sidecar, which holds suspect rows flagged by the advisory detector, not gate
  refusals, and is a review aid rather than an audit record.

Consequences: an operator cannot answer "what did the gate refuse for this
space last week, and why" without having captured every response; the
`directed:<model>@directed-policy-v2` attribution exists on accepted facts but
there is no counterpart for refused nominations; and the refusal counts used in
evidence records cannot be regenerated from the database.

Confirmed from source; not reproduced live. Related in spirit to the M16
durable job audit, which records job outcomes but not per-nomination gate
verdicts.

## Scope and boundaries

- Refusals must not enter `facts`, `entities`, `mentions` or any collection
  that promotion, attestation or materialization consumes. A new generated
  collection (for example `construction_refusals`) alongside `side_views` and
  `fact_semantics` in `GENERATED_COLLECTIONS` keeps the boundary.
- Record the gate that refused, the policy revision, the model attribution,
  the nominated triple, the chunk id and the evidence quote as submitted. Do
  not store the full chunk text again; the chunk is already addressable.
- Per-tenant retention and size caps are required, as for durable jobs.
- Independent of [CG-88](CG-88.md) and [CG-89](CG-89.md).

## Resolution

Implemented under the
[refusal ledger decision](../decisions/decision_construction_refusal_ledger.md),
which records the owner's choices: `skips`/`skipped` strings stay and a
parallel `refusals` array is added; a fixed 10,000-row per-tenant cap that
drops the newest; CGQL as the read path instead of a new route; deterministic
keys; and a ledger write failure that is reported, never fatal to the
construction. Change record:
[v2.7.22](../changelog/2026-09-22-construction-refusal-ledger.md).

Code: `crates/cognigraph-construct/src/refusals.rs` (gate codes and the
`Refusal` record, returned by `gate_directed_proposals`), a `gate` code on
`ProposalSkip`, `crates/cognigraph-server/src/refusals.rs` (ledger, cap,
keys, response attach), `construction_refusals` in `GENERATED_COLLECTIONS`,
and the wiring in the directed and propose routes. Docs: dataops guide
section 6b, HTTP reference rows, OpenAPI responses.

Edge cases covered by tests: all eight directed gates and every proposal
gate code; NFC-canonical and whitespace-only fields; duplicate nominations
in one request and across requests (first writer wins); key partitioning by
origin, space, gate, chunk and evidence but not by actor or wording; the cap
boundary including a zero cap and a known row at the cap; optional and
Unicode fields; the collection being generated, read-only through the
guarded backend and CGQL, and present in exports; a request that grounds no
facts; a request with no refusals writing nothing; and the response attach
on a ledger error.

## Acceptance

- [x] Every skip returned by `/construct/directed` and `/construct/propose` is
      also written, in the same request, to a read-only generated collection
      with gate name, policy revision, attribution, triple, chunk id, evidence
      quote and timestamp.
- [x] A read route or CGQL example in `docs/dataops/04-semantic-neurons.md`
      lists refusals per space and per gate, and a CLI export includes them
      (CGQL examples; export passes generated collections through, tested).
- [x] Regression test: a fixture nomination that fails each directed gate
      (eight codes across the six gate categories) produces exactly one
      refusal row per gate, and the write is skipped without error when the
      collection is at its cap.
- [x] The ledger tests prove the new collection is generated (not managed),
      read-only through the guarded backend and CGQL, and exported; being
      generated keeps it out of promotion and attestation by construction.
- [x] Retention and the tenant cap are documented in the dataops guide
      (section 6b) and the decision record; a sweeper remains later work.
