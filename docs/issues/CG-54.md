# CG-54: Review queue and space selectors silently truncate their datasets

- Status: Open
- Priority: P2
- Area: UI / review
- Found: 2026-09-11
- Verification: Source review and 201-neuron Enterprise browser/API reproduction

## Problem and evidence

[ReviewScreen.tsx](../../ui/src/screens/ReviewScreen.tsx), lines 34 and 64–74,
always requests `limit=200` without an offset and renders a table with
`pagination={false}` at line 311. Its count is only the loaded array length.
Both Review and Construct space selectors load at most 100 space documents.
There is no continuation or truncation indicator.

The isolated Enterprise server contained 201 valid proposed neurons in
`audit_space`. The browser rendered “200 neurons”, exactly 200 rows, no paging,
and no `audit-neuron-200`. An independent API request at offset 200 returned
that remaining neuron. [API page](../../ui/audit/2026-09-11-full-review/review-overflow.json),
[queue capture](../../ui/audit/2026-09-11-full-review/08-review-queue-200.png).
Reviewing/removing early rows may eventually expose later ones; the current
listing still misrepresents the pending queue. The 100-space boundary is
source-confirmed, not a separately seeded 101-space browser test.

[Full UI review and environment](../../ui/audit/2026-09-11-full-review/audit.md). No application fix was made in this audit.

## Acceptance

- [ ] Implement continuation/paging with truthful counts or explicit partial-result labels for review queues and space selectors.
- [ ] Ensure selection and graduation links can resolve items outside the initially loaded page.
- [ ] Browser-test more than 200 neurons and more than 100 spaces, including status changes and selected-item continuity.
