# CG-38: Read-only query route reports parse and validation errors as HTTP 500

- Status: Resolved
- Priority: P2

- Found: 2026-09-09 while verifying CG-28
- Reviewed revision: `9fb4933` (workspace 2.6.0)

- Resolved: 2026-09-09 (committed locally as `aae43ad`)

## Problem

Before this fix, `POST /api/search/query` wrapped `ExecutionError::Plan` as `QueryError`, producing
HTTP 500 for malformed or semantically invalid client queries. The read-write
`POST /api/query` route maps the same errors to `ValidationError` and HTTP 400.
Clients therefore see an internal server failure on the read-only surface for
an error they must correct themselves.

## Reproduction

Submit each query to both endpoints on a server with `/api/query` enabled:

```cgql
FOR d IN documents COLLECT WITH COUNT INTO n
RETURN LENGTH((FOR x IN documents RETURN 1))
```

```cgql
FOR d IN documents COLLECT group = 1
INTO xs = (FOR x IN documents RETURN x._key)
RETURN xs
```

The first fails parsing/desugaring; the second fails semantic validation.
Expected HTTP 400 on both routes. Before the fix, `/api/query` returned 400 and
`/api/search/query` returns 500, with the same underlying diagnostic. Neither
query should execute. No malformed writes are involved.

## Evidence

- [Read-only mapper](../../crates/cognigraph-server/src/routes/search/basic.rs),
  `cgql_error`, previously had no `ExecutionError::Plan` arm.
- [Read-write mapper](../../crates/cognigraph-server/src/routes/query.rs)
  explicitly classifies plan failures as validation errors.
- [Release observations](../evidence/engineering-historical-checks.md#artifact-8a8eb5bf06340e73565f):
  four `known_status_defect` entries reproduce HTTP 500 for these two cases
  across resident and paged storage; companion rejection entries show HTTP 400
  on `/api/query`. These are known failures, not passing desired behavior.

## Acceptance criteria

- Map client parsing and semantic-validation failures to HTTP 400 on the
  read-only query route, consistently with `/api/query`.
- Preserve forbidden 403, connection 503, and actual backend/execution failure
  mappings; do not turn backend errors into client mistakes.
- Add route-level regressions for parsing, validation, and backend error classes,
  then run all Rust gates and release HTTP checks on both query surfaces.
- Replace CG-28's known-status assertions with desired 400 assertions when fixed.

## Resolution

The read-only mapper now converts `ExecutionError::Plan` into a validation
error, matching the read-write route's 400 response and diagnostic prefix.
Typed forbidden, connection, and other execution/backend mappings are preserved.
New production-route tests cover parsing, validation, EXPLAIN/analysis, no
backend access for rejected plans, and continued runtime-error 500 responses;
existing fault-injection tests retain 403/503/500 coverage through HTTP and Lua.

Formatting, strict Clippy, all 955 reported Rust tests, five focused route
tests, and 147 query tests passed. Eight unconfigured Arango entries
early-returned. The saved release reproduced 24 incorrect statuses; all 288
corrected release HTTP/Lua observations passed in resident/paged Native modes,
including 48 plan-error responses and exact preservation after rejection.
The shared harness now requires 400 by default. See the
[verification report and evidence](query-error-status-2026-09-09.md).
