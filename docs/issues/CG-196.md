# CG-196: Offline repair for a store that already holds an unreadable document

- Status: Open
- Priority: P3
- Area: Native / recovery; CLI
- Found: 2026-11-11
- Verification: Pending (design gap recorded with CG-107 on 2026-11-11)
- Scheduling: After the P1 batch; no known store is affected

## Problem and evidence

Split out of [CG-107](CG-107.md). Since v2.7.47 Native refuses to write a
document nested deeper than 100 levels. A store written by an earlier version
can already hold a row that the JSON parser cannot read (more than 127 nested
containers). Such a store fails closed: a resident store does not open and a
paged store fails every scan of that collection. The error names the row,
for example "stored document `deep/d` cannot be read: recursion limit
exceeded".

There is no way to repair that store. The server will not start, and the CLI
has no offline command that removes or rewrites one row. The
[decision record](../decisions/decision_document_depth_limit.md) explains why
the store fails closed instead of skipping the row.

No store is known to be affected: the rows could only be produced by repeated
CGQL or Lua writes that wrap a value in itself.

## Acceptance

- [ ] An offline CLI command lists unreadable rows in a store and, on request, removes one or exports its raw bytes, without starting the server and without touching other rows.
- [ ] The command refuses to run against a store that a server holds open, and writes the repaired store through the existing private, no-replace file path.
- [ ] A test builds a store with an unreadable row, repairs it, and reopens it in resident and paged modes.
