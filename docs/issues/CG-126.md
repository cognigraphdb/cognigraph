# CG-126: CGQL compares and groups integers through f64 and writes integer literals as floats

- Status: Open
- Priority: P2
- Area: CGQL / numeric semantics
- Found: 2026-11-11
- Verification: Pending (reproduced live on 2026-11-11, 2.7.39 Community release build)

## Problem and evidence

`==`, `!=`, `IN`, filter pushdown and UPSERT matching compare
`left.as_f64() == right.as_f64()`
(`crates/cognigraph-query/src/executor/eval.rs:96`, `:220-222`,
`crates/cognigraph-core/src/types/predicate.rs:58`). COLLECT and DISTINCT key
on f64 bits (`executor/pipeline.rs:182-189`). Every numeric literal is parsed
as f64 (`parser/expr.rs:24-28`) and written back as a float.

Reproduced:

- With documents whose `big` is 9007199254740993 and 9007199254740992,
  `FILTER d.big == 9007199254740993` returns both.
- `INSERT { _key: "n", n: 1 } INTO docs RETURN NEW.n` returns `1.0`.

By the same code, `RETURN DISTINCT d.snowflake_id` and `COLLECT` merge
different 64-bit ids, and `UPSERT { ext_id: @id } …` updates a different
document whose id rounds to the same f64.

The set functions have the opposite problem inside nested values: `UNIQUE`,
`INTERSECTION` and `MINUS` compare nested numbers with `serde_json` equality,
where integer `1` differs from float `1.0` (`functions/value.rs:26-41`,
`:273-321`). Since literals are floats and stored values are usually integers,
`INTERSECTION(d.pairs, [[1,2]])` never matches, although
`docs/reference/cgql.md:348-351` promises numeric equality inside nested
arrays and objects. The unique index is a third rule: it treats `7` and `7.0`
as distinct.

## Acceptance

- [ ] Integer-to-integer comparison, grouping and UPSERT matching are exact; integer literals stay integers on write.
- [ ] The set functions use the same deep equality as `==`, and the relation to unique-index identity is documented.
- [ ] Tests cover values above 2^53 in `==`, `IN`, COLLECT, DISTINCT and UPSERT, and nested integer/float mixes in the set functions.
