# CG-150: Dump importer dry run stages a full copy of the data in the shared temp directory

- Status: Open
- Priority: P2
- Area: CLI / ArangoDB dump importer
- Found: 2026-11-11
- Verification: Pending (source-confirmed in the 2026-11-11 review; not executed)

## Problem and evidence

A dry run uses `std::env::temp_dir().join("cognigraph-arangodump-<uuid>")`,
created with `fs::create_dir`, and opens a full paged Native store inside it
(`crates/cognigraph-cli/src/arangodump/publish.rs:20-32`, `load.rs:44-50`).
The dry run loads every document. With a normal umask the directory is 0755
and the redb file 0644; the modes are inferred from the calls, not observed.
Staging is removed only on a normal drop.

Consequences:

- On a multi-user host any local user can read `store.redb`, holding all the
  dump's documents, while the dry run runs or after a killed run.
- Where the temp directory is memory-backed or small, a dry run of a large
  dump exhausts memory or disk and exits 4, although the real import beside
  `--output` would fit. `docs/reference/arangodump-import.md` tells operators
  to run the dry run first.

Two smaller issues in the same module: `--report` compares paths lexically
(`publish.rs:82`), so `./shop.redb` against `shop.redb` passes and the report
is renamed over the just-published store; and import staging has the same
default permissions.

## Acceptance

- [ ] Staging directories are created 0700 and store files 0600, for dry runs and imports.
- [ ] Dry-run staging goes beside `--output` or to an explicit staging directory, or the dry run validates without persisting document bodies.
- [ ] The report path is compared after canonicalization; tests assert the modes and that a killed dry run leaves nothing readable by others.
