# CG-171: Proposal error paths record misleading refusals or drop them

- Status: Open
- Priority: P3
- Area: Construct / proposals; refusal ledger (Enterprise)
- Found: 2026-11-11
- Verification: Pending (source-confirmed in the 2026-11-11 review; not executed)

## Problem and evidence

Gaps left after [CG-90](CG-90.md), which is otherwise intact:

- `propose_neurons_via_backend` discards a text-search error with
  `if let Ok(hits) = …` (`crates/cognigraph-construct/src/propose.rs:171-188`).
  The gap is then skipped as "no candidate evidence chunks mention the
  endpoints" with gate `proposal_rejected`, which the server writes to the
  ledger. A propose request that runs while the text index is rebuilding
  ([CG-99](CG-99.md)) durably records refusals for lack of evidence although
  the search simply failed.
- In the propose route, a storage error mid-loop returns before
  `record_refusals` (`crates/cognigraph-server/src/routes/construct/proposal.rs:161-209`).
  The refusals gathered so far are dropped and neurons already stored go
  unreported.
- On a ledger failure, `attach` returns `refusals: []` and
  `refusals_dropped: 0` (`refusals.rs:150-200`), and a test pins this.
- Two overlapping propose requests with the same gap can both insert; the
  second atomic batch fails on the duplicate key and loses all of that
  request's rows (plausible; the race was not reproduced).

## Acceptance

- [ ] A search failure is surfaced as a request error or a distinct gate code.
- [ ] Refusals collected before an error are recorded or returned; on a ledger failure the response still carries the rows with `stored: false` and a true dropped count.
- [ ] Duplicate ledger keys are skipped rather than failing the batch; tests cover each path.
