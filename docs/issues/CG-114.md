# CG-114: CLI export can replace a good backup with garbage and writes snapshots world-readable

- Status: Resolved
- Priority: P1
- Area: CLI / backup
- Found: 2026-11-11
- Verification: The release CLI was run against a stub server (truncated, HTML and other bad responses) and against a real authenticated 2.7.50 release server; both test suites pass (845 Community, 1,072 Enterprise)
- Resolved: 2026-11-11

## Problem and evidence

`send()` in `crates/cognigraph-cli/src/client.rs:75-94` maps a 2xx response
whose body cannot be read or parsed to the JSON string
`"<non-JSON response>"` and returns success. `Command::Export`
(`crates/cognigraph-cli/src/main.rs:80-91`) pretty-prints whatever came back
and writes it with `std::fs::write`: truncate-then-write, umask-default mode,
no fsync. It prints "snapshot written" and exits 0.

Failure sequences for `cognigraph export --out snapshot.json`:

- The connection resets mid-body, the client timeout in [CG-147](CG-147.md)
  fires during the body read, or a proxy or the console fallback answers 200
  with HTML. The file now holds the literal string, the previous good backup
  at that path is gone, and the exit code is 0.
- A crash or full disk mid-write leaves a truncated file in its place.
- The snapshot holds password hashes and all tenant data
  (`docs/operations/recovery.md` says to keep snapshots private) but is
  typically created 0644.

The same file already has `write_new_private_file` (0600, staged, fsynced,
no-replace), used by `references repair` and custody plans. The swallowed
parse error also makes every other command report success on an unparseable
2xx response.

## Resolution

- `send()` in `crates/cognigraph-cli/src/client.rs` reads the whole body and
  parses it. A 2xx response whose body cannot be read or is not JSON is an
  error for every command; an empty body is `null`. Error messages show the
  start of the body.
- `export` requires a `collections` object before it writes or prints.
- `export --out` writes through `write_new_private_file`: mode 0600, a synced
  staging file, a no-replace rename and a synced parent directory. An
  existing destination is refused and left untouched; there is no overwrite
  flag, by decision.

The [decision record](../decisions/decision_cli_export_safety.md) explains
the no-overwrite choice; the CLI guide describes the behaviour.

Tests (`crates/cognigraph-cli/tests/export_cli.rs`) run the real binary
against a stub server: a complete snapshot is written with mode 0600; a body
truncated below its declared length, cut-off JSON, an HTML page, an empty
body, a JSON string, JSON without `collections`, a 500 and an HTML 502 each
exit 1 and write nothing, with and without `--out`; an existing file survives
both a bad and a good response; no staging file is left behind.

Live check with the release CLI against a real 2.7.50 server with
authentication on: the first export writes a 0600 file containing the four
collections; a second export to the same path exits 1 with "it will not be
replaced"; a URL that serves no API and a bad token each exit 1 and write
nothing.

The 30-second client timeout that makes a truncated body likely is
[CG-147](CG-147.md).

## Acceptance

- [x] A 2xx response whose body cannot be read or parsed is an error (exit 1) for every command.
- [x] `export --out` writes 0600 through stage, fsync and rename, only after a fully received snapshot with a `collections` object; an existing destination is refused or replaced atomically behind an explicit flag.
- [x] Tests use a local stub that returns 200 with a truncated and with an HTML body, and assert the old file survives and the mode is 0600.
