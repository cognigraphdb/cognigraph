# CG-18: Text-index cache keys conflate distinct field lists

- Status: Resolved
- Priority: P2
- Area: Native text-search correctness
- Found: 2026-09-08
- Reviewed revision: `bc4bff1` (workspace 2.6.0; current drafts where noted)
- Verification: Source-confirmed

## Problem

Text-index memory keys and persistent-directory hashes serialize fields with `join(",")`. Distinct lists such as `["a,b"]` and `["a","b"]` have identical keys. A cached index can consequently answer a later request using the wrong schema and field population.

## Evidence

`crates/cognigraph-native/src/memory/search.rs:194-216`; `crates/cognigraph-native/src/memory/paged.rs:83-108`.

## Reproduction / comparison

Store documents with an `a,b` property and separate `a`/`b` properties containing different terms. Search one field list and then the other without a write between calls. Their in-memory cache key is identical, so the second request can reuse the first index.

## Acceptance criteria

Use an unambiguous structured encoding of collection and ordered field identity for cache keys/hashes; verify exact requested schema on warm-open; cover delimiter-bearing property names and restart behavior.

## Resolution — 2026-09-08

Native cache keys serialize `(collection, ordered fields)` as JSON; persistent
paths hash that identity and save it beside the index. Warm opens require the
same identity, exact schema, and generation. Regression tests and release-server
HTTP checks distinguish `["a,b"]` from `["a","b"]` in both storage modes across
restart. All Rust gates passed; see [batch verification](fixes-2026-09-08.md).
The separate server hybrid result-cache fingerprint is tracked in [CG-31](CG-31.md).

Verify the affected runtime or documentation contract before closure. Rust changes require all repository gates. See [review evidence](review-2026-09-08.md).
