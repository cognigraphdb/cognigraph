# CG-68: Qualify and document the Native-only release

- Status: Open
- Priority: P2
- Area: Release / documentation
- Found: 2026-09-12
- Verification: Pending

## Problem and evidence

Current architecture, setup and workflow material describes Arango maintenance
support, while the new [decision](../decisions/decision_native_only.md) selects
Native-only delivery. Preparation must remain labelled as planned until the
implementation exists; after removal, leaving active Arango setup instructions
would mislead operators and future agent work.

The [batch plan](../plans/native-only-2026-09-12.md) identifies affected surfaces
and the release boundary. The earlier UI/Rust/Docker evidence belongs to its
original revision; it does not qualify Native-only deployment readiness.

## Scope and dependencies

Final integration task after [CG-65](CG-65.md) and [CG-67](CG-67.md).
The owner confirms no prior delivery or live deployment; CG-64/CG-66 are optional
deferred backlog and do not block this gate. Reconcile current code docs, commands,
architecture, root instructions, relevant skills, packaging and executable
checks with the implemented Native-only behavior. Preserve resolved tickets,
old outcomes, fixture manifests and sealed captures as historical evidence.

Write active documentation as a Native-only product, removing old backend choices
and maintenance/deprecation narratives. Keep history in dated engineering records
and compatibility comparisons only where they serve external migration education.
Record any required sibling product/website and A9 teaching-material alignment
with its owner/path; locating or describing that work is not evidence it was
edited or published. This code ticket must distinguish repository-local readiness
from separate product publication.

## Acceptance

- [ ] Active architecture, configuration, running/recovery/CLI guides, decision inventory, implementation plan, `.env.example`, root instructions and relevant skills describe Native directly with working links/examples and no legacy backend choice.
- [ ] Audit remaining Arango/AQL references: retain useful external migration education and dated evidence, and remove active backend-support or deprecation narratives. Mark optional dump tooling as deferred.
- [ ] Document fresh Native setup and first-deployment prerequisites. Remove the earlier required customer inventory, last-Arango release, migration/cutover and backward-compatibility requirements.
- [ ] On the final candidate, pass the full applicable shared CI suite, default/Enterprise checks, current browser regressions, both Linux/amd64 Docker/runtime checks and applicable Helm live backup checks. Execute fresh Native API/Lua/search/snapshot/restart and applicable configuration-validation journeys without Arango or importer dependencies.
- [ ] Store a versioned acceptance record bound to commit, edition, fixture hashes, commands, results and intentional exclusions. Distinguish local evidence from remote CI, release and deployment outcomes.
- [ ] Apply the normal version increment and changelog in the authorized push workflow, with the owner's pre-deployment breaking-change exception. A 3.0.0 jump is not imposed solely for backend removal; inspect incoming work and verify the final candidate.
- [ ] Record Native-only readiness explicitly before any first live deployment. Do not equate passing local checks or publishing source/images with completed deployment.
