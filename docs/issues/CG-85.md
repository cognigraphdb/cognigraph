# CG-85: Bind variables in LIMIT for client-controlled pagination

- Status: Resolved
- Priority: P2
- Area: Query language / CGQL
- Found: 2026-09-20
- Verification: Query-crate corpus, error-path and pushdown tests, Native corpus on all storage modes, both server editions and the full local gate before the local develop merge on 2026-09-22
- Resolved: 2026-09-22
- Scheduling: Deferred optional backlog; reconsider after the first external application integration is ready to start (owner decision 2026-09-20)

## Problem and evidence

[The CGQL specification](../reference/cgql.md) accepts only literal integers in
`LIMIT`, and [the AQL migration guide](../reference/aql-to-cgql.md) tells callers
that `LIMIT @n` is unsupported and to "interpolate client-side". Bind variables
are otherwise strict and validated before storage access, which makes `LIMIT` the
one clause where an application must splice user-controlled numbers into query
text.

Paginated list endpoints are the most common query shape in application code,
and `LIMIT @offset, @count` is the idiom migrating callers already have.
Interpolating it creates an injection surface that the bind-variable design
exists to remove, prevents reuse of a single query string across pages, and
forces every consumer to write the same integer validation.

This is a language gap confirmed from the specification at 2.7.15, not a
reproduced defect.

## Scope and dependencies

Independent of [CG-84](CG-84.md), [CG-86](CG-86.md) and [CG-87](CG-87.md).
Grammar, validation, planning and executor ownership stay in `cognigraph-query`.
The existing `LIMIT 0` rejection and the source-row and time budgets are
unchanged in meaning; only the value source widens.

## Resolution

Implemented under the
[decision record](../decisions/decision_limit_bind_variables.md), which fixes
the contract: each `LIMIT` operand is a literal or a bind variable; bound
values must be non-negative integer JSON numbers (no coercion of strings or
floats); zero and too-large counts raise the literal errors; every `LIMIT`
in the plan tree is resolved after the bind-variable presence check and
before the first scan; pushdown is unchanged with resolved values; plain
`EXPLAIN` renders bind names. Change record:
[v2.7.25](../changelog/2026-09-22-limit-bind-variables.md).

Code: `limit_value` in the grammar, `LimitValue` in the AST (literal keeps
its JSON number shape, binds serialize as `{"bind": name}`), the parser and
bind-name collector, literal-only checks in validation with a new
`LimitBindNotInteger` error, `max_limit` carried on the plan, and
`executor/limit.rs` for resolution, pre-check and EXPLAIN rendering, used by
the pipeline, scan pushdown and vector search.

Edge cases covered by tests: strings, floats including `2.0`, negatives,
booleans, null, arrays and objects for both operands; zero, the maximum
plus one and `u64::MAX` counts; offsets of zero, past the end and
`u64::MAX`; a missing count reported before an invalid offset; an extra
bind rejected; one bind reused for both operands; a bind shared with the
projection; a bind inside a `LET` subquery and after `COLLECT`; pushdown of
the resolved value and its unchanged disabling conditions; failure before
any backend call; EXPLAIN and EXPLAIN ANALYZE rendering; the AST and plan
serialization shapes.

## Acceptance

- [x] `LIMIT @count` and `LIMIT @offset, @count` accept bind variables that
      resolve to non-negative integers, with the same pre-execution validation
      errors as other bind variables for missing, non-integer or negative values.
- [x] `LIMIT` pushdown is unchanged for bound values; `EXPLAIN` keeps its
      shape and renders the bind names where a literal would show its value.
- [x] Corpus cases under `crates/cognigraph-query/tests/corpus/` cover `exec/`,
      `validate_err/` and `parse_err/` for the new forms, and both engines agree.
- [x] `docs/reference/cgql.md` and the `LIMIT @n` row of the migration guide are
      updated in the same change.
