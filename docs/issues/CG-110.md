# CG-110: Typed traversal and graph-augmented search accept unbounded depth outside every budget

- Status: Resolved
- Priority: P1
- Area: Server / graph; Native / traversal
- Found: 2026-11-11
- Verification: Reproduced live on 2026-11-11 (2.7.39); after the fix depths 5 to 10 on the same graph return HTTP 400 in about 35 ms at 133 MiB on a 2.7.49 Community release build; both test suites pass (841 Community, 1,068 Enterprise)
- Resolved: 2026-11-11

## Problem and evidence

`POST /api/graph/traverse` and `POST /api/search/graph-augmented` pass
`max_depth: u32` (and `seed_limit`) straight to Native. Native enumerates every
simple path breadth-first and clones the full vertex and edge documents for
each partial path (`crates/cognigraph-native/src/memory/search.rs:54-94`,
`memory/paged.rs:194-247`). CGQL caps traversal depth at 10; these routes and
Lua `graph.traverse` do not. The work is synchronous inside the async handler
and holds the state read lock, so neither `COGNIGRAPH_REQUEST_TIMEOUT_SECS`
nor the CGQL budgets apply, and writers wait behind it.

Reproduced on a complete graph of 10 documents (45 edges), `direction: "any"`,
with a 5 s request timeout and both CGQL budgets set:

| `max_depth` | Response | Time | Server RSS |
|---|---|---|---|
| 4 | 5 MB | 0.04 s | 78 MiB |
| 6 | 161 MB | 1.6 s | 2.0 GiB |
| 8 | 1.6 GB | 27.7 s | 5.5 GiB |
| 50 | none after 59 s | – | 5.6 GiB |

The traverse route needs graph-write scope, but graph-augmented search is open
to any role that can search.

## Resolution

- **Depth cap.** `max_depth` above 10 is refused with HTTP 400 on
  `/api/graph/traverse` and the graph-augmented route, and with a script
  error in Lua `graph.traverse` (`cognigraph_core::check_traversal_depth`).
- **Path budget.** Both Native traversal loops (resident and paged) stop with
  a validation error once a traversal expands more than 10,000 paths
  (`MAX_TRAVERSAL_PATHS`). The budget is charged before the documents along a
  path are copied, and it applies to every caller, CGQL included.
- The read-only query route returns a backend input error as 400.

The reasoning, including why the budget is a constant and why a time budget
alone was rejected, is in the
[decision record](../decisions/decision_search_and_traversal_limits.md).

Tests: `crates/cognigraph-native/tests/traversal_bounds.rs` serves depth 4 on
the ten-document complete graph (3,609 paths) and refuses depths 5 to
`u32::MAX` in memory-only, resident and paged modes; a 40-step chain is
served at any depth; a hub with exactly 10,000 spokes is served and one more
is refused. Route tests cover the depth cap on both routes and the budget
within the cap; a Lua test covers the binding.

Live check on a 2.7.49 release server, same graph as above:

| `max_depth` | Before | After |
|---|---|---|
| 4 | 5 MB, 0.04 s | 5 MB, 0.04 s, 78 MiB |
| 6 | 161 MB, 1.6 s, 2.0 GiB | HTTP 400 in 0.04 s, 133 MiB |
| 8 | 1.6 GB, 27.7 s, 5.5 GiB | HTTP 400 in 0.03 s, 133 MiB |
| 50 | no response | HTTP 400 (depth cap) in under 1 ms |

A CGQL traversal `1..8` over the same graph also returns HTTP 400.

Not changed: the traversal still runs synchronously under the read lock. Its
duration is now bounded by the budget, but it cannot be interrupted, and it
does not consult the CGQL time budget ([CG-111](CG-111.md)).

## Acceptance

- [x] Native enforces a maximum depth and a path or visited budget and returns a bounded error; `TraversalOpts` carries the limits. As built: the path budget is in Native and the depth cap at the typed entry points, both as core constants rather than option fields.
- [x] The HTTP routes and the Lua binding apply the same cap as CGQL, and the traversal honours the time budget. The cap is applied; the time budget is not consulted, which the path budget makes unnecessary for memory and CG-111 tracks for time.
- [x] A test on a small complete graph with a large `max_depth` finishes within the budget in resident and paged modes.
