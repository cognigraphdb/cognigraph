# CG-139: Directed construction silently merges distinct entities whose names share an ASCII key

- Status: Open
- Priority: P2
- Area: Construct / directed identity
- Found: 2026-11-11
- Verification: Pending (source-confirmed in the 2026-11-11 review; not executed)

## Problem and evidence

`sanitize` in `crates/cognigraph-construct/src/ingest.rs:431-456` keeps only
ASCII alphanumerics for the entity key. Rule ingest fails closed on a key
collision (`ingest.rs:122-129`; the real-label construction decision calls it
"an error rather than a silent semantic merge"). The directed path instead
does `entities.entry(key).or_insert_with(...)` and adopts whatever is stored
under that key (`directed.rs:148-163`, `directed/gates.rs:201-221`). Fact
edges carry only `_from`/`_to` keys, not the nominated surface, and the dedup
set also keys on `entity_key`, so a second distinct nomination is dropped
without a refusal.

Failure cases:

- Targets `5%` and `$5` both get key `5` and land on one entity named after
  the first writer. The same holds for Greek-letter variants of one protein
  name and for names that differ only in a non-ASCII letter.
- `C++` and `C#` produce a self-loop.
- `finalize_draft` (`draft/finalize.rs:141-196`) merges such entities and
  rewrites the second entity's rules onto the first, reported only as a
  "merged" skip. Names with no ASCII characters all share the empty key.

## Acceptance

- [ ] Directed construction adopts a stored entity only when the names are equal under a defined equivalence (for example case and whitespace); otherwise it refuses with a recorded gate code or uses a collision-free key.
- [ ] Draft canonicalization does not merge names that differ beyond case.
- [ ] Tests cover symbol-only and non-ASCII differences.
