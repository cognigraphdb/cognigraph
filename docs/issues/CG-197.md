# CG-197: CGQL execution holds an async runtime worker for its whole time budget

- Status: Resolved
- Priority: P2
- Area: CGQL / server runtime
- Found: 2026-11-11
- Verification: A test reproduced the starvation on v2.7.56 (a health request waited 2.6 s behind two long queries on two workers) and passes on the fix; a 2.7.57 Enterprise release server with two runtime workers was driven over HTTP on both routes; both test suites (888 Community, 1,119 Enterprise) and the Native runtime harness pass
- Resolved: 2026-11-11

## Problem and evidence

Split out of [CG-111](CG-111.md). A CGQL query fetches its sources with
`await` and then runs joins, filters, `COLLECT`, `SORT` and projection
synchronously inside the request future (`executor/run.rs`,
`executor/pipeline.rs`). Since v2.7.53 the query's own time budget ends that
work, and it defaults to the request timeout, but until then the query keeps
one Tokio worker thread busy. The same holds for the search route that runs
CGQL (`routes/search/basic.rs`). Lua already runs on a blocking thread.

Failure sequence: on a server with N runtime workers, N concurrent queries
that each use their full time budget leave no worker for other requests,
health checks included, for up to the request timeout (30 seconds by
default). The per-IP rate limit does not prevent it when the requests come
from several addresses or the limit is off, which is the default.

The [decision record](../decisions/decision_cgql_execution_budgets.md) lists
this as a known consequence.

## Resolution

The [decision record](../decisions/decision_cgql_execution_off_runtime.md)
has the reasoning and the alternatives.

- Both routes call one runner (`cgql_runner.rs`). It runs the whole query on
  a blocking thread, re-entering the request's tenant context there, and
  the handler only awaits the result.
- At most `COGNIGRAPH_CGQL_MAX_CONCURRENT_QUERIES` queries run at once
  (default: the number of CPUs). Others wait for a slot; the wait does not
  use the time budget and is bounded by the request timeout (408).
- The executor takes a `Cancellation` flag and reads it at every deadline
  check. The runner raises it when the request future is dropped, on a
  client disconnect or the request timeout. Lua's script cancellation
  raises it for a running `graph.query()`, which a cancelled script could
  not stop before.
- A supervisor task outlives the request and sweeps cached results after a
  read-write query, also when the query was cancelled.
- The default time budget is now nine tenths of the request timeout. The
  timeout can fire while a query runs, so an equal budget would always
  lose to a bare 408.

Tests: `cgql_runner_tests.rs` holds two long queries on a two-worker
runtime and requires health within a second, on both routes; it also covers
waiting behind the limit, a dropped request (running and queued) and the
cache sweep. An Enterprise test checks tenant scoping. `cgql_cancellation.rs`
(Native) and `deadline_tests.rs` cover the flag.

Live check, 2.7.57 Enterprise release binary, two runtime workers, one
twelve-CPU laptop: with six long queries running, 51 health probes answered
in at most 0.6 ms on either route. Under a 10-second request timeout each
long query answered 422 for `time` after 9.0 seconds. With one slot and a
60-second budget, a client disconnect freed the slot within 3 ms, and a
dropped write wrote nothing. A query still running at a 5-second request
timeout answered 408 and was stopped.

Not done: Lua scripts are not counted against the limit; storage calls made
by other routes still run on the async workers; the slot wait is not
reported in metrics; the cost of the thread hand-off was not measured.

## Acceptance

- [x] The CPU-bound part of a CGQL query runs off the async workers (a blocking pool or a dedicated one) with a bounded number of concurrent executions, or yields to the runtime at a bounded interval.
- [x] A test holds as many long queries as there are workers and shows that a health request still answers within a second.
- [x] The time budget and the other budgets behave as before, and cancellation of the HTTP request stops the query at its next deadline check.
