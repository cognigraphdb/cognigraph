# CG-29: Server completion selection ignores the documented provider override

- Status: Resolved
- Priority: P2
- Area: Provider configuration
- Found: 2026-09-08
- Reviewed revision: `bc4bff1` (workspace 2.6.0; current drafts where noted)
- Verification: Reproduced with the saved pre-fix release; required Rust gates, 13 fixed release server configurations, 13 rejected startups, and 3 benchmark runs passed

## Problem

The server constructs its completion provider directly from key availability, preferring OpenAI whenever its key exists. It never reads `COGNIGRAPH_COMPLETION_PROVIDER`, although `.env.example`, the side-view decision, and the shared completion helper expose that override. Side-views can follow the override while the main construction provider silently uses a different provider, leading to unexpected routing, cost, or model errors.

## Evidence

`crates/cognigraph-server/src/main.rs:274-298`; `crates/cognigraph-embeddings/src/completion.rs:217-244,273-293`; `.env.example:42-53`; `docs/decisions/decision_sideviews_provider_and_benchmark.md:45-59`.

## Reproduction / comparison

Configure both keys and set `COGNIGRAPH_COMPLETION_PROVIDER=gemini`. The main server branch still creates OpenAiCompletion; the side-view resolver can select Gemini. No external provider request was made for this finding.

## Acceptance criteria

Use one validated provider-selection contract across server and harnesses, including base URL and model handling. Reject invalid explicit provider values rather than silently choosing another. Add startup tests for each provider, both-key precedence, missing keys, and inherited side-view configuration.

Verify the affected runtime or documentation contract before closure. Rust changes require all repository gates. See [review evidence](review-2026-09-08.md).

## Resolution — 2026-09-08

Server startup and harness helpers now use the shared `CompletionConfig`
resolver for provider, key, model, and base URL selection. Explicit overrides
take precedence, side-views inherit consistently or use their separately
selected provider's default model, and invalid explicit configurations fail
startup before stores open. Provider-free startup remains supported.

All 888 tests, formatting, Clippy, and real release HTTP/harness checks passed.
The pre-fix release sent an explicitly Gemini-selected construction request to
OpenAI; the fixed release sent construction and inherited side-view requests to
Gemini with the configured model. See [implementation, compatibility, and live
evidence](completion-provider-2026-09-08.md). Changes remain uncommitted.
