# CG-145: Job archive pagination cannot be followed without an explicit cutoff, and the CLI cannot page at all

- Status: Open
- Priority: P2
- Area: Server / jobs archival; CLI (Enterprise)
- Found: 2026-11-11
- Verification: Pending (source-confirmed in the 2026-11-11 review; not executed)

## Problem and evidence

The archive cursor fingerprint hashes `before_ms`
(`crates/cognigraph-server/src/jobs/archival.rs:23-35`, `:133-144`). When the
client omits it, the server uses `now − retention`, which differs on every
call, and `ArchiveResult` does not return the resolved cutoff. The CLI's
`job archive` has no `--cursor` (`crates/cognigraph-cli/src/args.rs:168-173`,
`:975-1011`). A call without a cursor scans only the first `limit × 16` rows
by key.

Failure cases:

- An HTTP client follows the documented flow in
  `docs/operations/jobs.md:240-246` (omit `before_ms`, follow `next_cursor`)
  and gets 400 "invalid or stale archive cursor" on page two.
- Through the CLI, or with repeated cursor-less calls, once the first scan
  window holds only ineligible rows every call returns `eligible: 0` with a
  non-null `next_cursor`. Older eligible jobs beyond the window are never
  archived.
- A CLI dry run only ever shows the first window.

Every archival test passes `cursor: None` and an explicit `before_ms`.

## Acceptance

- [ ] The response returns the resolved `before_ms`, or the cursor carries the cutoff.
- [ ] The CLI accepts `--cursor`.
- [ ] Tests cover multi-page archival with an omitted `before_ms` and with a leading window of ineligible rows.
