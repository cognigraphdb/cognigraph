# CG-106: CGQL mutations ignore the collection part of a full document id

- Status: Resolved
- Priority: P1
- Area: CGQL / mutations
- Found: 2026-11-11
- Verification: Reproduced live on 2026-11-11 (2.7.39); after the fix the same statement returns HTTP 400 on a 2.7.46 Community release build and both documents survive; both test suites pass (827 Community, 1,054 Enterprise)
- Resolved: 2026-11-11

## Problem and evidence

`crates/cognigraph-query/src/executor/mutation.rs:181-185` reduces a mutation
key with `raw.rsplit_once('/')` and keeps what follows the last slash. The
collection prefix is never compared with the mutation's target collection.
The split is also from the right, while `PARSE_IDENTIFIER`
(`functions/value.rs:109-111`) splits from the left because a key may contain
`/`.

Reproduced with `persons/42` and `organizations/42` stored:
`REMOVE "organizations/42" IN persons` returns 200 and deletes `persons/42`;
`organizations/42` is untouched. UPDATE and REPLACE use the same helper. The
natural edge pattern `FOR e IN rels REMOVE e._to IN persons` therefore writes
to whichever `persons` document shares a key with the edge's target, and
`REMOVE "a/b" IN docs` targets key `b`. No test passes a full id.

## Resolution

`document_key_of` in `crates/cognigraph-query/src/executor/mutation.rs` now
takes the target collection. A string without `/` is a plain key. A string
with `/` is split once from the left and must name the target collection;
otherwise the row fails with `MutationKeyOutsideCollection` before its write.
The HTTP mutation route returns that error, and a non-string key, as 400
instead of 500. The rule and the rejected alternatives are in the
[decision record](../decisions/decision_mutation_key_ids.md); the
specification's mutation rules state it.

Tests (`crates/cognigraph-native/tests/mutation_keys.rs`): an id of another
collection is refused for REMOVE, UPDATE and REPLACE and the same-key
document survives; `FOR e IN member_of REMOVE e._to IN persons` is refused
and works against the right collection; plain keys and full ids of the target
both work; `REMOVE "a/b" IN docs` no longer deletes `docs/b`, and
`REMOVE "docs/a/b" IN docs` removes key `a/b`; empty parts and a different
letter case are refused.

Live check on a 2.7.46 release server: `REMOVE "organizations/42" IN persons`
and `REMOVE "a/b" IN docs` return HTTP 400 and leave `persons/42` and
`docs/b` in place; `UPDATE "persons/42" …` and `REMOVE "42" IN persons` work.

UPSERT was not changed: its `_key` search field was always a plain key. In a
multi-row mutation the rows before a failing row stay applied.

## Acceptance

- [x] A full id whose collection differs from the mutation target is an error before any write.
- [x] Key extraction agrees with `PARSE_IDENTIFIER` for keys that contain `/`.
- [x] Corpus cases cover mismatched prefixes and slash-containing keys for REMOVE, UPDATE, REPLACE and UPSERT, and `docs/reference/cgql.md` states the rule.
