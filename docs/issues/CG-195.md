# CG-195: Decide whether Renovate's schedule and limits can keep up with dependency updates

- Status: Open
- Priority: P3
- Area: Workflow / dependency automation
- Found: 2026-11-11
- Verification: Pending (dashboard state read on 2026-11-11)
- Scheduling: Owner decision

## Problem and evidence

Split out of [CG-192](CG-192.md). `.github/renovate.json` schedules Renovate
for a four-hour window on Mondays (`* 0-3 * * 1`, Europe/Bucharest) with
`prConcurrentLimit: 3` and `prHourlyLimit: 2`. On 2026-11-11 its dashboard
listed 28 updates as "awaiting schedule" and no pull request was open; the
last merged pull request was from 2026-09-23. In that time the dependency and
advisory gates went from passing to failing with 11 advisories, and the drift
was found only by running the gates by hand.

At three pull requests a week, 28 updates take more than two months to
arrive, and each one must pass a freshness gate that fails while the others
are still pending. Why no pull request was opened inside the window was not
investigated.

Options to decide between:

- Widen the window and raise the limits, with grouping so that one pull
  request can satisfy the freshness gate.
- Keep Renovate for visibility only and do refreshes as tickets, as CG-83,
  CG-92 and CG-192 did, on a fixed cadence.
- Add a scheduled run of the dependency and advisory suites, like the
  toolchain canary of [CG-151](CG-151.md), so drift is reported without
  waiting for a push.

## Acceptance

- [ ] The owner's choice is recorded in a decision, and the Renovate configuration and the develop-gate guide follow it.
- [ ] Advisory drift on the default branch is reported within a stated time without a manual run.
