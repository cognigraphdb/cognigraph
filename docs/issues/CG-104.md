# CG-104: Lua scripts reach os, io and jit through the leftover module() global

- Status: Resolved
- Priority: P1
- Area: Lua / sandbox
- Found: 2026-11-11
- Verification: Reproduced live on 2026-11-11 (2.7.39); after the fix the same three scripts are refused over HTTP on a 2.7.44 Community release build, and both test suites pass (815 Community, 1,042 Enterprise)
- Resolved: 2026-11-11

## Problem and evidence

`crates/cognigraph-lua/src/runtime.rs` loads `StdLib::ALL_SAFE`, which includes
`io`, `os`, `package` and `jit`, and then hides them by setting their globals
to nil (lines 79-82 and 135-148). LuaJIT's package library also registers the
global `module`, which the sandbox leaves in place. `module(name)` looks the
library up in the registry's `_LOADED` table, where the hidden libraries still
live, and makes it the environment of the calling chunk.

Reproduced through `POST /api/lua/execute` with
`COGNIGRAPH_LUA_INSTRUCTION_LIMIT=100000`:

- `module("os"); return {rc = execute("true")}` returns `{"rc":0}`;
  `getenv` and `remove` are callable too.
- `module("io"); local f = popen("echo cg-sandbox-probe"); return f:read("*a")`
  returns `"cg-sandbox-probe\n"`.
- `module("jit"); on(); while true do end` never returns. The worker stayed at
  100% CPU after the client disconnected and after SIGTERM. The same loop
  without `jit` stops with "Script exceeded instruction limit".

Any role with the Lua execute scope, including the read-only script runner,
can run shell commands as the server user and read its environment and files.
This reopens [CG-1](CG-1.md) (JIT can be switched back on) and removes the
basis of the [CG-81](CG-81.md) disposition that no script reaches
`io`/`os`/`package`. The sandbox tests only assert that the named globals are
nil. Other limits of the Lua runtime are in [CG-129](CG-129.md).

## Resolution

The Lua state no longer loads `io`, `os`, `package`, `debug` or `ffi`
(`crates/cognigraph-lua/src/runtime.rs`). It loads `table`, `string`, `math`
and `bit` on top of the base library. `jit` is loaded only to switch
compilation off and is then removed from the globals and from the registry's
loaded and preload tables. Engine construction now fails if a forbidden
global exists or the registry holds a library outside the allow-list. The
reasoning and the rejected alternative are in the
[decision record](../decisions/decision_lua_sandbox_libraries.md).

Tests: `tests/sandbox.rs` pins the exact list of script globals, runs 19
escape attempts (including the three above, through `pcall`, `getfenv`,
`rawget` and a coroutine) and checks that the instruction limit holds when a
script tries to re-enable the JIT. `src/runtime_tests.rs` checks the registry
contents and that a state built the old way is refused.

Live check on a 2.7.44 release server with
`COGNIGRAPH_LUA_INSTRUCTION_LIMIT=100000`: the `os`, `io` and `jit` scripts
each fail with "attempt to call global 'module' (a nil value)", the bare loop
stops with "Script exceeded instruction limit", and a script using `string`,
`math` and `bit` still returns its result.

Scripts lose `os.time`, `os.date` and `os.clock`; no documented example used
them. Stopping `print` from writing to the server's output and adding a
memory limit remain in [CG-129](CG-129.md).

## Acceptance

- [x] `io`, `os`, `package` and `jit` are never loaded into the script state (preferred), or `module` and every other route to `_LOADED` is unreachable.
- [x] Regression tests call `module("os")`, `module("io")`, `module("jit")` and `module("package")` and each fails; the live HTTP harness asserts the same.
- [x] `docs/architecture/lua.md` and the CG-81 disposition note describe the sandbox as built.
