# CG-59: Collection search and filters present partial matches as complete results

- Status: Resolved
- Priority: P2
- Area: UI / collections
- Found: 2026-09-11
- Verification: Source review, 161 UI tests and Rust-served Native browser/API checks with 126 documents

## Problem and evidence

The collection browser promises search over the whole collection but fixes
text-search `limit` at 100 and treats the returned array length as the complete
pagination total ([CollectionsScreen.tsx](../../ui/src/screens/CollectionsScreen.tsx),
lines 104–119 and 191–205). Category and embedding filters run only against
`activeDocs`; in an unsearched listing that is one server page, and the category
picker is populated from that page alone.

With 101 synthetic documents sharing one search term, the browser displayed
“1–25 of 100” while the collection heading said 101. The same real search API
with limit 200 returned 101 matches. Before search, page one offered only
`first-page`; the `later-only` category stored on subsequent pages was absent.
[Counts](../../ui/audit/2026-09-11-full-review/collection-search.json),
[search capture](../../ui/audit/2026-09-11-full-review/11-collection-search-1067.png).

The server-side listing itself pages correctly; the defect is the UI's implied
completeness of search and filtering. This does not reopen the previously fixed
off-page exact-key lookup.

[Full UI review and environment](../../ui/audit/2026-09-11-full-review/audit.md). No application fix was made in this audit.

## Acceptance

- [x] Page or continue search results where supported, or explicitly label the result cap instead of presenting it as the total.
- [x] Apply category/embedding filtering to the intended dataset, or label it clearly as filtering the loaded page.
- [x] Test more than 100 search matches and categories/embedding states present only beyond page one, with truthful counts and reset behavior.

## Resolution — 2026-09-11

The collection browser labels the current API contract: up to 100 text matches
plus a deduplicated exact-key lookup, with an explicit warning when the text
limit is reached. Pagination counts **retrieved** documents, not all possible
matches. Category choices and filters are scoped to the loaded collection page
when browsing and to retrieved documents when searching.

Filtered page counts use the loaded-page denominator. Next-page availability
uses the unfiltered page/catalog, so an empty filtered page cannot strand the
operator. Selected categories remain identifiable across pages; search filter
changes return to page one, result pages are clamped after filtering, and Reset
restores collection browsing. Unknown catalog counts remain unknown.

Search errors retain their source and disclose partial results, with Retry.
Changed queries and retries clear previous results immediately; obsolete
completions cannot publish. Routine health probes do not discard results or
restart the search. Inspectors follow documents visible in the current view.

## Verification and bounds

- UI lint/types, 161 tests (22 files, 783 assertions), production build and
  documentation/registry checks pass.
- The real Native fixture contains 125 matching documents plus a separate
  exact-key document. API limit 200 returns 125 text hits; the UI retrieves
  100 plus the exact key and displays `1–25 of 101 retrieved`, with the cap
  warning and a terminal fifth page.
- Ready embeddings and the `later-only` category exist beyond page one.
  Filtered-empty page one still advances, page two shows 24 ready rows out of
  25 loaded, and Reset restores `1–25 of 126 documents`.
- Off-page exact-key lookup, no matches, filtered search pagination, health-poll
  stability, delayed search, partial failure and keyboard Retry pass. Scaled
  desktop layouts retain visible scope text and pagination with internal table
  scrolling.

[Browser/API report and sealed evidence](../../ui/audit/2026-09-11-collection-search-scope/audit.md).
No backend pagination/cursor or full-collection facet API was added. This is
explicitly bounded retrieval and page-local browsing filters. No Rust changes,
model calls, remote CI or publication; ArangoDB was not exercised.
