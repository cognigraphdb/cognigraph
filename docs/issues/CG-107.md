# CG-107: A document nested deeper than 128 levels cannot be read back and blocks startup

- Status: Resolved
- Priority: P1
- Area: Native / persistence
- Found: 2026-11-11
- Verification: Reproduced live on 2026-11-11 (2.7.39); after the fix the 100th update is refused with HTTP 400 on a 2.7.47 Community release build and the server restarts on that store; both test suites pass (832 Community, 1,059 Enterprise)
- Resolved: 2026-11-11

## Problem and evidence

Writes serialize with `serde_json::to_string` and no depth check
(`crates/cognigraph-native/src/storage.rs:495`). Every read path parses with
`serde_json::from_str`, which stops at 128 nested containers; the workspace
does not enable `unbounded_depth`. HTTP request bodies are parsed with the same
limit, so the gap is reachable through values built inside the server: CGQL
expressions and Lua tables.

Reproduced: `FOR d IN deep UPDATE d._key WITH { n: { n: d.n } } IN deep` run
135 times; every call returned 200. After a restart the server panicked at
`crates/cognigraph-server/src/main.rs:182` with "Failed to open native storage
… recursion limit exceeded at line 1 column 710" and did not start. In paged
or sidecar mode the same row fails every scan of its collection instead: list,
filter, derivative rebuild and export.

Write access to one collection is enough to make the whole store unopenable.

## Resolution

Native now refuses a document that nests arrays and objects more than 100
levels deep (`MAX_DOCUMENT_DEPTH`). The check sits in `NativeBackend::persist`
(`crates/cognigraph-native/src/memory/mod.rs`), which every write path
reaches with or without a store behind it, before anything is committed. The
walk uses an explicit stack. CGQL carries the refusal as `InvalidInput`, and
the HTTP routes return 400. The limit, why it is below the parser's 128, and
the alternatives are in the
[decision record](../decisions/decision_document_depth_limit.md).

A store that already holds an unreadable row still fails closed, by decision:
skipping the row would make a document vanish from reads, exports and backups
with only a log line. The error now names the row. An offline repair for such
a store is [CG-196](CG-196.md).

Tests: `tests/document_depth.rs` runs create, update, replace, atomic batch,
bulk insert, both edge paths and snapshot import at the limit and one level
over, in memory-only, resident and paged modes, then reopens the persistent
stores; it also runs the reproduction above until it is refused and reopens.
`src/storage_depth_tests.rs` covers the depth accounting, a 200,000-level
value on a 256 KiB thread, and the named error for an unreadable row.

Live check on a 2.7.47 release server: the wrapping update succeeds 99 times,
the 100th returns HTTP 400 naming `deep/d`; a direct 101-level document is
refused and a 100-level one accepted; after a restart the server is healthy
and both documents are readable.

## Acceptance

- [x] Every write path (create, update, replace, batch, bulk, import, edges, CGQL, Lua) refuses a document the store could not re-read, before anything is persisted.
- [x] A store that already holds such a row still opens; the row is reported rather than failing startup or a whole scan, and that choice is recorded. Decided otherwise: the store fails closed and names the row; the decision record says why, and CG-196 tracks the repair tool.
- [x] A regression test stores depth 127, is refused above the limit on each path, and reopens the store.
