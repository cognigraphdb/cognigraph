# CG-49: Production console always targets API port 3001

- Status: Resolved
- Priority: P1
- Area: UI / deployment
- Found: 2026-09-11
- Verification: Source review and fresh production-bundle browser reproduction

## Problem and evidence

The built console served by Rust at `http://127.0.0.1:38471` loads its assets,
but every API request targets `127.0.0.1:3001`. A fresh session shows an offline,
admin-labelled shell with “Failed to fetch” instead of reaching the server's
login. Direct `/health` on port 38471 returns 200. There is no visible API-origin
setting to recover the session.

[App.tsx](../../ui/src/App.tsx), lines 35–45, unconditionally constructs port
3001 even though its comment promises same-origin behavior for Rust serving.
The saved session override does not help a first visitor. The API client's
network-error auth probe then treats the unreachable server as ungated.

Reproduction: build `ui/`, serve it with `COGNIGRAPH_UI_DIST` on a port other
than 3001, leave 3001 unused and open `/collections` in a fresh browser tab.
[Captured DOM](../evidence/ui-2026-09-11-full-review.md#artifact-ad3fe2d2bf03fe961a5b) and
[screenshot](../evidence/ui-2026-09-11-full-review.md#artifact-f152ec39fa0b368615e8)
show the wrong destination. Subsequent audit flows used a temporary forwarding
proxy on 3001; their success does not resolve this finding.

[Full UI review and environment](../evidence/ui-2026-09-11-full-review.md#artifact-2a08bd45b55e9bd0cb9c). No application fix was made in this audit.

## Acceptance

- [x] Use the load origin for production API requests and an explicit development configuration for the split-port Bun setup.
- [x] Give an unreachable or unverified server an honest connection/authentication state.
- [x] Run fresh-session login, direct links, reload and an authenticated operation against Rust serving on a non-3001 origin; preserve the Bun development flow.

## Resolution — 2026-09-11

Production uses the browser page origin, including its scheme/host/port. Bun
HTML development inlines an explicit public API-port setting via `bunfig.toml`;
the production build defines that setting as null. A failed saved target can
be reset with its token/session, avoiding credential reuse at another origin.

The auth probe now requires a recognizable successful protected catalog read.
401 requests login; 403/404/429/5xx, network errors, timeouts and malformed
responses do not establish access. Console routes remain unmounted while
checking or unverified, with an explicit Retry action and neutral identity copy.

[Live report](../evidence/ui-2026-09-11-production-origin.md#artifact-a495041e72ddd34399af) verifies fresh
login and a persisted document edit on a non-3001 Rust origin, deep links/reload,
default and custom Bun ports, offline retry, clearing a saved target/session,
and confirmed authentication-disabled mode. UI checks, 92 tests and build pass.
HTTPS/IPv6 origin formatting is unit-tested; no live TLS/IPv6 deployment or full
Rust suite is claimed by this UI-only change.

### Enterprise follow-up during CG-51 — 2026-09-11

The first resolution's live coverage was Community only. CG-51 exposed that a
host-admin receives 403 from `/api/collections`, correctly lacking tenant-data
access. The probe now verifies `/api/tenants` on that specific denial, requiring
a recognizable successful tenant catalog before opening the console. Both
requests share the existing timeout. Denial itself never grants access.

New tests cover successful control-plane verification, malformed/failing fallback
responses and session expiry. Fresh host-admin login and reload passed against
real Enterprise; an ordinary data admin remained denied tenant management.
[Follow-up evidence](../evidence/ui-2026-09-11-tenant-deletion.md#artifact-0ec008ada9942ef8213a). The earlier
sealed report remains unchanged and does not claim this additional coverage.
