# CG-49: Production console always targets API port 3001

- Status: Open
- Priority: P1
- Area: UI / deployment
- Found: 2026-09-11
- Verification: Source review and fresh production-bundle browser reproduction

## Problem and evidence

The built console served by Rust at `http://127.0.0.1:38471` loads its assets,
but every API request targets `127.0.0.1:3001`. A fresh session shows an offline,
admin-labelled shell with “Failed to fetch” instead of reaching the server's
login. Direct `/health` on port 38471 returns 200. There is no visible API-origin
setting to recover the session.

[App.tsx](../../ui/src/App.tsx), lines 35–45, unconditionally constructs port
3001 even though its comment promises same-origin behavior for Rust serving.
The saved session override does not help a first visitor. The API client's
network-error auth probe then treats the unreachable server as ungated.

Reproduction: build `ui/`, serve it with `COGNIGRAPH_UI_DIST` on a port other
than 3001, leave 3001 unused and open `/collections` in a fresh browser tab.
[Captured DOM](../../ui/audit/2026-09-11-full-review/fresh-origin-dom.txt) and
[screenshot](../../ui/audit/2026-09-11-full-review/01-production-wrong-origin.png)
show the wrong destination. Subsequent audit flows used a temporary forwarding
proxy on 3001; their success does not resolve this finding.

[Full UI review and environment](../../ui/audit/2026-09-11-full-review/audit.md). No application fix was made in this audit.

## Acceptance

- [ ] Use the load origin for production API requests and an explicit development configuration for the split-port Bun setup.
- [ ] Give an unreachable or unverified server an honest connection/authentication state.
- [ ] Run fresh-session login, direct links, reload and an authenticated operation against Rust serving on a non-3001 origin; preserve the Bun development flow.
