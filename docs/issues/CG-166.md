# CG-166: A subquery in a mutation's RETURN runs before the write and cannot see NEW or OLD

- Status: Open
- Priority: P3
- Area: CGQL / mutations
- Found: 2026-11-11
- Verification: Pending (reproduced live on 2026-11-11, 2.7.39 Community release build)

## Problem and evidence

`desugar_subqueries` (`crates/cognigraph-query/src/parser/mod.rs:168-186`)
lifts RETURN subqueries into body LETs for mutation queries too. The body
runs before the per-row write, and NEW and OLD are not in scope there
(`executor/mutation.rs:26-29`, `:172-176`). The placement table in
`docs/reference/cgql.md` covers selectors and payloads but not a mutation's
RETURN.

Reproduced with four documents in `docs`:
`INSERT {a:1} INTO docs RETURN LENGTH((FOR d IN docs RETURN 1))` returns 4,
the count before the insert. By the same code,
`UPDATE "k" WITH {…} IN docs RETURN (FOR x IN refs FILTER x.to == NEW._id RETURN x)`
fails with "identifier `NEW` is not in scope".

Smaller parser notes from the same review: `bind_var` is not atomic, so
`FILTER d.x == @ n` yields a bind named `" n"` while `LIMIT @ n` yields `n`;
the reserved-word list omits the mutation keywords; and UPSERT without `_key`
lists the whole collection once per row without charging the row budget
(`executor/mutation.rs:130-135`).

## Acceptance

- [ ] Subqueries in a mutation's RETURN are either rejected with a specific diagnostic or evaluated after the write with NEW and OLD bound.
- [ ] The specification table and the corpus cover the case.
- [ ] The bind-variable token is atomic, and UPSERT matching charges the row budget.
