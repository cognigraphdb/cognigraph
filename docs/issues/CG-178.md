# CG-178: Promotion contract leaves reject, principal identity and channel generation undecided

- Status: Open
- Priority: P3
- Area: Server / promotions and governance (Enterprise)
- Found: 2026-11-11
- Verification: Pending (source-confirmed in the 2026-11-11 review; not executed)
- Scheduling: Owner decisions needed; no implementation before they are recorded.

## Problem and evidence

Four places where the code follows the decision records as written but the
records leave a gap. Each needs an owner decision.

- **Reject is not terminal.** `decide` never looks up prior decisions for the
  evidence (`promotions/decision_transition.rs:72-115`), and chain validation
  has no rule for a reject beyond "no head value". After one promoter signs a
  reject on a gate-passing bundle, another promoter (or the same one with a
  new key) can promote it while the head is unchanged. History shows reject,
  then promote, with no step in between.
- **Separation of duties compares `principal_id` strings.** Registration
  rejects one principal with two purposes but never checks whether
  `subject_user_key` already holds a key under another principal
  (`governance/key_registration.rs:33-40`, `:104-112`). Identifiers are only
  NFC-checked, so `ops-lead`, `Ops-Lead` and `ops-lead ` are three
  principals. One user account whose role changes can author a policy under
  one principal and promote under another. This needs a root signature, so it
  is defence in depth rather than a bypass.
- **Generation is not pinned.** The signed policy and approval carry only the
  target and the resolved policy. The first evidence bundle on a channel,
  even a failed one, fixes its authority generation
  (`promotions/generation_boundaries.rs:63-76`). A promoter can register an
  M19-generation bundle first on a channel the approver expected to require
  byte-verified M23 inputs.
- **Document drift.** `decision_m19_signed_governance_separation_of_duties.md`
  (lines 312-313) says the promotion decision stores three principal ids; it
  stores the promoter's only (`promotions/decision_contracts.rs:91-117`).

## Acceptance

- [ ] Each of the first three points has a recorded decision, and the code and tests follow it (promote after reject, role change mid-flow, minimum generation).
- [ ] Principal identifiers have a canonical form.
- [ ] The M19 decision matches what the decision record stores.
