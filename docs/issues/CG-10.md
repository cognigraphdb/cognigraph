# CG-10: Paged document reads can remain stale after a committed concurrent write

- Status: Resolved
- Priority: P1
- Area: Native paged storage
- Found: 2026-09-08
- Reviewed revision: `bc4bff1` (workspace 2.6.0)
- Verification: Deterministic concurrency reproduction and release HTTP regression

## Problem

Paged update/replace releases the state write lock after redb commit but before updating the document cache and vector sidecar. A later writer can commit and publish its cache value first, then the earlier writer can overwrite that cache with older data. Independently, a cache-miss reader can read an old redb snapshot and cache it after a newer write. These caches are not checked against a per-document revision, so the inconsistency can persist beyond the overlapping requests.

## Evidence

- `crates/cognigraph-native/src/memory/documents.rs:145-157,204-216` — cache/sidecar publication after dropping the write lock.
- `crates/cognigraph-native/src/memory/paged.rs:245-279` — cache-miss fetch and insertion without a version check.
- `docs/redb-primary-design.md` — redb is authoritative and the LRU is a derivative.

## Reproduction / failure sequence

Interleaving: A commits version 1 and releases the state lock; B commits version 2 and caches it; A then caches version 1. Subsequent `get_document` returns cached version 1 even though export/reopen sees redb version 2. This schedule follows directly from the lock boundaries; a deterministic scheduler-controlled reproduction is still required during remediation.

## Acceptance criteria

- [x] Keep commit and derivative publication in one ordered critical section, or version cache/sidecar entries and reject stale publication.
- [x] Protect cache-miss fills against intervening writes and deletes.
- [x] Add deterministic concurrency tests for update/update, read/update, replace/delete, and vector sidecar consistency; verify against redb export and reopen.

## Resolution — 2026-09-08

Paged update, replacement, and deletion retain the state write lock through
cache and vector-delta publication. Point reads hold the read lock through
catalog checks, redb fetch, and cache fill. Sidecar rebuilds also hold that
boundary and serialize publication, preventing an old build from replacing a
newer vector view and later being stamped current by another key's delta.

Controlled tests reproduced stale versions, resurrected deleted rows, and
missing vector candidates on the original implementation. They now pass,
including comparisons with redb truth, export, and reopen. Formatting, Clippy,
all 857 tests, and release HTTP concurrent-access/restart checks passed for
paged cached, paged zero-cache, and resident-sidecar profiles. See
[verification and scope](paged-cache-2026-09-08.md).

Run the repository Rust gates and a focused runtime regression before closing this issue. See [review evidence](review-2026-09-08.md).
