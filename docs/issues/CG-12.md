# CG-12: In-flight requests can resume into a recreated tenant's store

- Status: Resolved
- Priority: P1
- Area: Tenant isolation
- Found: 2026-09-08
- Reviewed revision: `bc4bff1` (workspace 2.6.0)
- Verification: Reproduced in the pre-fix release; six regression tests, all Rust gates, and fixed resident/paged release HTTP lifecycle checks passed

## Problem

Authentication checks the tenant once and stores only its name in task-local state. Every subsequent RoutedBackend method looks that name up again. Retirement evicts the current handle and recreation permits the same name, so a request admitted for the previous incarnation can resume after an awaited provider call and write into the replacement store. The comment that old requests keep an Arc to the quarantined inode is insufficient: the handler retains the routing facade, not a pinned store.

## Evidence

- `crates/cognigraph-server/src/auth_middleware.rs:80-98` — one-time tenant check and name-only scope.
- `crates/cognigraph-server/src/tenancy.rs:75-87,107-119,173-176,192-208` — name lookup per operation.
- `crates/cognigraph-server/src/routes/tenants.rs:248-275` — fences jobs/promotions and retires store.
- `crates/cognigraph-server/src/routes/construct.rs:150-159` — provider-backed operation using the routing facade.

## Reproduction / failure sequence

Admit a directed or embedding request for tenant incarnation A and pause its provider response. Delete A and recreate the same tenant name as incarnation B. When the old request resumes, its next backend method resolves the newly registered B store. This is source-confirmed; a controlled paused-provider HTTP lifecycle regression remains part of closure.

## Acceptance criteria

Earlier remediation context (2026-09-08): [CG-3](CG-3.md) holds the
promotion transition lock across directed provider execution and
reconciliation. Tenant retirement waits for that admitted directed operation
to drain. That mitigated the directed example; this batch closes the general
request-routing race and the shared-control-store user-administration window.

- [x] Pin each admitted request to an immutable tenant incarnation and store handle, or revalidate incarnation under a mutation fence before every delayed write.
- [x] Prevent an old request from opening a new store for a deleted name, even before recreation.
- [x] Test suspended/deleted/recreated tenants while synchronous provider-backed requests are in flight, alongside the existing durable-job lifecycle tests.

## Resolution — 2026-09-08

Admission captures the original store, cache, and incarnation under the tenant
lifecycle lock. Lua transfers that context to its worker and supervisor;
user/token administration holds a lifecycle guard through its live-identity
check and shared-control-store operation. Admitted ordinary requests may
drain against quarantined data, as T4 specifies, without reaching a replacement
tenant. Formatting, Clippy, all 869 tests, release build, and real HTTP
deletion/recreation/suspension/restart checks passed in resident/paged modes.
See [verification, reproduction script, and tradeoffs](request-isolation-2026-09-08.md).
