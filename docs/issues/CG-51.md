# CG-51: Tenant deletion confirmation promises recovery that recreation does not provide

- Status: Resolved
- Priority: P1
- Area: UI / tenants
- Found: 2026-09-11
- Verification: Browser deletion of an isolated synthetic tenant plus HTTP and filesystem verification

## Problem and evidence

[TenantsScreen.tsx](../../ui/src/screens/TenantsScreen.tsx), line 184, asks:
“Delete the … record? Its users are refused until it is recreated.” The page and
success toast likewise describe deleting a record. This implies temporary
suspension recoverable by recreating the name.

The actual [tenant deletion handler](../../crates/cognigraph-server/src/routes/tenants.rs),
lines 246–276, retires work, deletes the tenant's accounts and tokens, and
quarantines its store. The response includes `quarantined`, which the UI ignores.
The [tenant deletion decision](../decisions/decision_tenant_deletion.md) defines
this stronger lifecycle.

The browser deleted the disposable `audit-deletion` tenant after its admin had
written one document. Recreating its name returned 200, but both the old login
and session returned 401. A new administrator had to be bootstrapped. The old
store remained as `audit-deletion.redb.deleted-…`, not an automatically restored
active store. [Confirmation](../evidence/ui-2026-09-11-full-review.md#artifact-b83745efb93c5735aa64)
and [HTTP/filesystem evidence](../evidence/ui-2026-09-11-full-review.md#artifact-020a2bb4e2e1a5d3642c).
This is a misleading destructive confirmation, not a server isolation failure.

[Full UI review and environment](../evidence/ui-2026-09-11-full-review.md#artifact-2a08bd45b55e9bd0cb9c). No application fix was made in this audit.

## Acceptance

- [x] State account/token removal, work retirement and data quarantine before confirmation; distinguish deletion from suspension.
- [x] Explain that recreating a name does not restore credentials or data, and report the actual deletion response.
- [x] Exercise cancel and confirmed deletion against a disposable tenant with data and credentials, including attempted access after recreation.

## Resolution — 2026-09-11

A dedicated confirmation dialog names the tenant and explains account/token
removal, queued work/promotion retirement, data quarantine and separate operator
recovery. It recommends Suspend for a temporary access pause and explicitly
states that same-name recreation does not restore credentials or data.

The page validates and displays the actual `deleted` and `quarantined` response,
including an already-absent record or no quarantined entries. A failed or invalid
response keeps the dialog open with an unconfirmed-outcome warning and requires
closing/refreshing before another attempt. Cancel restores focus to the row
action; completed deletion returns focus to Refresh after the catalog reload.

[Executed browser/HTTP report](../evidence/ui-2026-09-11-tenant-deletion.md#artifact-0ec008ada9942ef8213a):
cancel preserved the synthetic document and credentials; confirmed deletion
quarantined the store and invalidated login, JWT and API-token access. Same-name
recreation produced a new incarnation; old credentials remained invalid and a
newly bootstrapped administrator saw an empty catalog. Real empty-store,
already-deleted and disconnected-request scenarios also passed.

The same run corrected CG-49's missing host-admin probe coverage: the console
verifies the protected tenant catalog after the data catalog refuses that role.
UI lint/types, 96 tests and production build pass. No Rust implementation changed;
work retirement follows the existing server contract and was not stress-tested
with running jobs in this UI verification.
