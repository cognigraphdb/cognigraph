# CG-108: Requests rejected by the auth middleware are logged without a tenant and shown to every tenant's admin

- Status: Resolved
- Priority: P1
- Area: Server / tenancy / observability
- Found: 2026-11-11
- Verification: A release Enterprise server with two tenants was driven over HTTP (a viewer's 403, an anonymous and a bad-token 401) and each admin's log view read back; both test suites pass (848 Community, 1,076 Enterprise)
- Resolved: 2026-11-11

## Problem and evidence

`admit` in `crates/cognigraph-server/src/auth_middleware.rs` attaches
`TenantTag` to the response only after `next.run`, on the success path. Every
rejection (bad or expired token, role lacking the scope, suspended tenant)
returns an error response with no tag. `record_metrics` in `hardening.rs` then
stores the event with `tenant: None`, and `RecentErrors::snapshot` returns
`None` events to every caller. The comment at `hardening.rs:35-38` says these
events carry no tenant-specific data, but each event records the method, the
path and the message.

Failure sequence in a multi-tenant Enterprise server: a viewer in tenant B
sends `DELETE /api/documents/patients/p-123` and gets 403. The admin of tenant
A calls `GET /api/admin/logs` and reads that method, path (collection and key)
and message. Rejections of a suspended tenant also put the tenant name in the
message. The existing test `logs_are_scoped_to_the_callers_tenant` only covers
events that were tagged beforehand.

## Resolution

- `admit` in `auth_middleware.rs` now records the caller's tenant as soon as
  the caller is identified: after a session token's signature and expiry
  verify, and after the user behind a token is loaded. Every rejection issued
  from then on (missing scope, suspended or deleted tenant, stale identity,
  store unavailable) carries `TenantTag` and is stored under that tenant.
- `RecentErrors::snapshot` takes a `redact_unattributed` flag. Events with no
  tenant are still listed, but on a multi-tenant server a tenant admin sees
  their path reduced to the first two segments (`/api/documents/…`). Method,
  status, time and message are kept. A single-tenant server shows the full
  path, since its admin is the operator.
- The stored event and the stdout log line are unchanged.

The [decision record](../decisions/decision_error_log_attribution.md) gives
the reasons, including why unattributed events are redacted instead of
hidden. The HTTP reference and the operations guide describe the view.

Tests: `hardening_log_tests.rs` covers the snapshot for a tenant, another
tenant and the unscoped view, and the path reduction for short, long and
root paths. `auth_log_attribution_tests.rs` (Enterprise) sends a viewer's
403, a suspended tenant's request, an anonymous 401 and a bad-token 401
through the real middleware and metrics layer and reads `/api/admin/logs`
as the other tenant's admin.

Live check on the 2.7.51 Enterprise release binary with two tenants: a
`default` viewer's `DELETE /api/documents/patients/p-123` returned 403; the
`acme` admin's log showed neither that path nor the tenant, and showed the
two 401s as `GET /api/documents/…`; the `default` admin saw the 403 with its
full path.

A host administrator gets the same redacted view. A full cross-tenant view
would be a control-plane feature and is not built.

## Acceptance

- [x] A rejection issued after the user is resolved is tagged with that user's tenant.
- [x] Rejections that cannot be attributed (401) are hidden from tenant admins or have their path and message redacted.
- [x] A route test drives a 403 and a 401 through the middleware and the metrics layer and asserts another tenant's admin cannot see them.
