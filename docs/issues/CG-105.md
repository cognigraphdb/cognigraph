# CG-105: Deeply nested CGQL text overflows the stack and aborts the server

- Status: Resolved
- Priority: P1
- Area: CGQL / parser
- Found: 2026-11-11
- Verification: Reproduced live on 2026-11-11 (2.7.39); after the fix the same query returns HTTP 400 in about a millisecond on a 2.7.45 Community release build and the server stays up; both test suites pass (822 Community, 1,049 Enterprise)
- Resolved: 2026-11-11

## Problem and evidence

The pest parser is recursive descent and its call limit is off unless
`pest::set_call_limit` is called, which the repository never does. The AST
builder, subquery hoisting, validation and `Expr` drop recurse as well. Nothing
bounds query length or expression nesting before the parse
(`crates/cognigraph-query/src/parser/mod.rs`); the depth cap in
`validation.rs` covers subqueries only and runs after parsing. The parse runs
on a Tokio worker with the default stack.

Reproduced: `POST /api/search/query` (the read-only route) with
`RETURN ((((…1…))))` nested 100,000 deep, a 200 KB body. The server printed
"thread 'tokio-rt-worker' has overflowed its stack / fatal runtime error:
stack overflow, aborting" and exited. A stack overflow is not a panic, so no
handler can catch it. Every tenant goes down, and Lua `graph.query()` reaches
the same parser. Nested arrays and repeated `NOT` take the same path. The only
nesting case in the corpus is five levels deep.

## Resolution

`parse_query` now runs a lexical pre-scan
(`crates/cognigraph-query/src/parser/limits.rs`) before the grammar. It
refuses text longer than 262,144 bytes, nesting deeper than 32 and expression
depth beyond 256, with an ordinary parse error. The scan is linear and does
not recurse. Width does not count as depth: a comma or a clause keyword ends
a chain. The limits, how they were measured and the rejected alternatives are
in the [decision record](../decisions/decision_cgql_text_limits.md), and the
specification has a [Query Text Limits](../reference/cgql.md#query-text-limits)
section.

The limits were sized from measurement on a 2 MiB thread: a release build
parses and executes about 156 nested arrays before the stack runs out, a
debug build 44. The parser release that arrived with [CG-192](CG-192.md) also
checks stack headroom, but only for the grammar and not for the later passes
or for long operator chains.

Tests (`crates/cognigraph-query/tests/query_limits.rs`): twelve hostile
constructs of 100,000 levels and five 10,000-operator chains are refused on a
256 KiB thread; queries exactly at each limit parse and execute; wide queries
(a 5,000-element array, 500 conditionals in a list, 300 `LET` clauses, a
500-field object) are accepted; brackets inside strings and comments are
ignored; malformed text gets a parse error. A release-only test runs the
worst accepted queries on a 1 MiB thread. Two corpus cases pin the boundary.

Live check on a 2.7.45 release server: 100,000 nested parentheses or arrays,
50,000 `NOT` and a 50,000-term `+` chain each return HTTP 400 within about a
millisecond; the worst accepted query (32 arrays around a 224-operator chain)
returns its result; the same refusal comes back through Lua `graph.query()`;
the server stays up.

Not covered: debug builds can still overflow on the worst accepted query, and
values from bind variables or stored documents are outside this check
([CG-107](CG-107.md)).

## Acceptance

- [x] Query length and expression nesting are bounded before or during parsing and return an ordinary 400 parse error.
- [x] Tests with at least 100,000 levels of parentheses, arrays and unary operators return that error on a 2 MiB thread, through HTTP and through Lua.
- [x] `docs/reference/cgql.md` states the limits.
