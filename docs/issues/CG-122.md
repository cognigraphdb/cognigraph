# CG-122: Snapshot import commits one transaction per document under the write lock and leaves a partial restore on failure

- Status: Open
- Priority: P2
- Area: Native / import and export
- Found: 2026-11-11
- Verification: Pending (source-confirmed in the 2026-11-11 review; not executed)

## Problem and evidence

`import_snapshot` in `crates/cognigraph-native/src/memory/mod.rs:373-434`
calls `self.persist(&ops)?` inside the per-document loop (`:414`), so each
document is its own redb commit with an fsync. The state write lock is held
for a whole collection. Documents are neither validated nor stamped: there is
no `_key`/`_id` check, non-objects are accepted, and the collection's existing
type is not checked. `triples_clear()` runs outside the lock (`:374`).

Consequences:

- Restoring 100,000 documents performs 100,000 fsyncs while every read and
  write on the backend is blocked.
- A unique violation or an invalid key halfway through returns an error with
  earlier collections and rows already committed.
  `docs/decisions/decision_unique_indexes.md` (item 3) says import refuses
  before any store change.
- An `upsert_edge` between two collections of the import can rebuild the
  triple index before the import rewrites that collection, so later upserts
  create duplicate edges (plausible; needs concurrent timing).

## Acceptance

- [ ] Import validates everything first and commits per snapshot (or per collection) in one transaction, or the non-atomic contract is documented and the decision record corrected.
- [ ] The triple index is invalidated under the write lock after the writes.
- [ ] A test imports a snapshot whose last row violates a unique index and asserts nothing was stored.
