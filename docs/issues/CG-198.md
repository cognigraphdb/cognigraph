# CG-198: CGQL budget and runtime errors answer HTTP 500

- Status: Resolved
- Priority: P2
- Area: Server / CGQL routes
- Found: 2026-11-11
- Verification: Both query routes were driven over HTTP on a 2.7.56 release server for each budget and each error group; both test suites (874 Community, 1,104 Enterprise) and the Native runtime harness pass
- Resolved: 2026-11-11

## Problem and evidence

Both query routes map every execution error they do not name to
`CogniGraphError::QueryError`, which answers HTTP 500
(`routes/query.rs`, `cgql_error` in `routes/search/basic.rs`). That includes
the four budget errors and the type errors a query can cause itself
(`ExpectedBool`, `ExpectedNumber`, `ExpectedArraySource`, an unknown bind
variable).

Seen live: `POST /api/search/query` with a cross product answered

```
HTTP 500  Query execution error: query exceeded its memory budget (1073741824 bytes)
```

and a query stopped by its time budget answered 500 as well.

A budget refusal is the designed outcome of a request the caller wrote, not a
server fault. As 500 it is logged at `warn`, counts as a server error in
metrics and monitoring, and tells a client to retry a request that will fail
the same way. [CG-38](CG-38.md) fixed the same thing for parse and
validation errors.

## Resolution

- `crates/cognigraph-server/src/cgql_errors.rs` holds the one function that
  turns an `ExecutionError` into a response. Both query routes call it; the
  two route-local copies are gone. The match has no catch-all, so a new
  error variant does not compile until its status is decided.
- Budget refusals answer **422** through the new
  `CogniGraphError::QueryBudgetExceeded`. The body has
  `code: "query_budget_exceeded"`, `budget` (`source_rows`,
  `intermediate_rows`, `memory`, `time`), `limit` and `unit`, and the
  executor's message. The time limit is read from the budget the query ran
  under. No `Retry-After` is sent.
- **400** for a missing or unexpected bind variable, an unknown identifier,
  function or collation locale, and a value of the wrong type (`FOR x IN 1`,
  `1 + "a"`, a non-boolean `FILTER`, an `UPSERT` search that is not an
  object). **403** for a mutation sent to the read-only route.
- **404** for a missing collection and for `UPDATE`/`REPLACE` of a missing
  document. The live check showed these reached the routes as a flattened
  backend failure, so the executor now carries the backend's
  `CollectionNotFound` and `DocumentNotFound` through as typed errors
  (`ExecutionError::DocumentNotFound` is new).
- A backend failure still answers 500 and an unavailable backend 503.

The [decision record](../decisions/decision_cgql_error_statuses.md) explains
the choice of 422 over 408, 429, 413 and 400. The HTTP reference has the
status table, the CGQL reference points to it, and the OpenAPI document
lists 404, 409 and 422 with a `QueryBudgetError` schema.

Tests (`cgql_errors_tests.rs`, both editions): every budget on both routes
with the typed body; a query exactly at its row budgets answers 200; seven
caller errors answer 400 on both routes; a mutation is refused with 403 on
the read route, runs on the write route and conflicts with 409 when
repeated; a missing collection answers 404 on both routes, with and without
`EXPLAIN ANALYZE`, and a mutation of a missing document 404; a table of 25
execution error variants pins each status, including 500 for a backend
failure and 503 for a lost connection. The existing route test with a
synthetic storage failure still expects 500. Two older tests pinned the
previous behaviour and were updated: `FOR x IN 1` answering 500, and a
failed `DOCUMENT()` lookup on a missing collection surfacing as a backend
error. The Lua tests that assert the budget messages are unchanged.

Two verification harnesses expected the old statuses and were updated: the
Native runtime harness (source-row refusal 422 with the typed body, mutation
on the read route 403; 348 checks per edition) and the subquery contract
harness (`FOR x IN 1` 400; 288 checks).

Live check: see the changelog record.

Not changed: `POST /api/lua/execute` still answers a script error for a
budget refusal inside `graph.query()`, and `GraphBackend::query` still
returns the flattened `QueryError`.

## Acceptance

- [x] The source-row, intermediate-row, memory and time budget errors answer a 4xx status chosen once and documented in the HTTP reference; the body names the budget and its limit.
- [x] Query type errors and a missing bind variable answer 400.
- [x] A backend or internal failure still answers 5xx.
- [x] Route tests cover one case of each group on both query routes, and Lua `graph.query()` errors keep their text.
