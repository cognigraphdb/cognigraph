# CG-131: One tenant's failed promotion recovery aborts startup for every tenant

- Status: Open
- Priority: P2
- Area: Server / startup; promotions (Enterprise)
- Found: 2026-11-11
- Verification: Pending (source-confirmed in the 2026-11-11 review; not executed)

## Problem and evidence

`crates/cognigraph-server/src/main.rs:496-511` handles a recovery error with
`panic!("promotion recovery failed for tenant …")`. At run time the same
condition is a per-tenant mutation latch with reads still served.
`validate_key_record` starts with `self.root_key()?`
(`governance/key_validation.rs:12`), so an unset
`COGNIGRAPH_GOVERNANCE_ROOT_PUBLIC_KEY` plus one stored governance key in any
tenant fails recovery.

Failure sequence: tenant A has one authority record that fails full validation
(out-of-band corruption, the cases in [CG-112](CG-112.md) and [CG-135](CG-135.md), or
the root variable dropped in a redeploy). On the next restart the process
exits before binding HTTP, for every tenant. The documented repair paths
(`GET /api/admin/promotions/status`, `POST /api/admin/promotions/recover`,
snapshot import) are unreachable.

The documents disagree with the code. The M19 decision says signed-governance
mutation "is unavailable and fails closed". `docs/operations/governance/deployment.md`
and the M18 decision describe a tenant latch cleared by Admin recover.
`docs/operations/jobs.md` documents a startup abort only for job recovery.
The comment on `configure_governance_root` says a missing root is permitted.

## Acceptance

- [ ] A promotion-recovery failure at startup latches that tenant (degraded health, mutations fenced) and the server starts; or the abort is a documented contract with an offline repair path.
- [ ] A missing root with stored signed authority degrades governance instead of failing the boot.
- [ ] A test with two tenants, one holding a corrupted decision, shows the other is served after restart.
