# CG-112: Reusing an Idempotency-Key across governance record kinds permanently breaks a tenant's promotion authority

- Status: Resolved
- Priority: P1
- Area: Server / governance (Enterprise)
- Found: 2026-11-11
- Verification: A regression test reproduces the failure sequence against the admission functions the routes call (it fails without the fix) and both test suites pass (848 Community, 1,077 Enterprise); the HTTP routes were not driven against a release binary
- Resolved: 2026-11-11

## Problem and evidence

`ensure_governance_idempotency_available_locked`
(`crates/cognigraph-server/src/governance/scoped_records.rs:128-160`) checks
five collections: governance keys, key revocations, policy revisions, policy
approvals and artifact attestations. Semantic-repair admission checks those
and its own two collections (`semantic_repairs.rs:1169-1201`), but the
governance side never looks at the semantic-repair collections. Stored-authority
validation (`governance/authority_validation.rs`) requires one idempotency
hash set across all seven kinds.

Failure sequence:

1. A policy author creates a semantic repair revision with
   `Idempotency-Key: K` (201).
2. Anyone later submits an artifact attestation, key registration, key
   revocation, policy revision or policy approval with the same `K`. Admission
   passes and the record is stored (201).
3. Every later reconcile fails with "governance records reuse an
   idempotency-key hash" and latches the tenant's promotion error. Promote,
   rollback, governed ingest and M26 build and deploy are blocked.
4. `recover_tenant` runs the same validation, so the latch never clears.
   Snapshot preflight of the data fails too.

The records are append-only and have no delete route. Only direct database
surgery repairs the tenant.

## Resolution

- `governance/idempotency_namespace.rs` defines `AuthorityRecordKind`: the
  seven signed record kinds, each with its collection. It is the only
  definition of the namespace.
- Admission: all seven paths (key registration, key revocation, policy
  revision, policy approval, artifact attestation, Semantic Repair revision
  and review) call `ensure_authority_idempotency_available_locked`, which
  checks every kind. The two older checks are removed. A spent key returns
  409 and stores nothing.
- Validation: `validate_governance_authority` ends with
  `GovernanceAuthority::ensure_idempotency_hashes_unique`, which iterates the
  same list. The seven scattered checks are removed.
- An exact replay is looked up before the namespace check and still returns
  the original record.

The [decision record](../decisions/decision_authority_idempotency_namespace.md)
explains why validation was not relaxed instead. The governance guide states
the rule.

Test (`promotions/tests/idempotency_namespace.rs`, Enterprise): a Semantic
Repair revision and a review each spend a key. An artifact attestation, a
key registration, a key revocation, a policy revision and a policy approval
that reuse one of those keys are each refused with a conflict and store
nothing. Reconcile and tenant recovery then succeed, and a snapshot of the
store imports into an empty one. The review request replays unchanged. The
refused attestation and approval succeed with keys of their own. The reverse
order (a revision reusing an attestation's key) is refused. A stored record
edited to carry a reused hash is still refused by recovery. With the
semantic-repair kinds taken out of the admission check, the test fails at
the attestation.

Not done: the HTTP routes were not exercised against a release binary,
because every request needs externally signed statements; the routes pass
the header straight to the functions under test and map the conflict to 409
as before. A store that already holds a cross-kind reuse is not repaired;
none is known.

## Acceptance

- [x] Admission of every governance and attestation record rejects an idempotency hash already used by a semantic repair revision or review, with 409.
- [x] Admission and stored-authority validation share one definition of the idempotency namespace.
- [x] A test creates a revision and then an attestation with the same key, gets 409, and reconcile and recover stay healthy.
