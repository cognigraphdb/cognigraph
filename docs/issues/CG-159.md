# CG-159: Rate limiting is per TCP peer, and timeouts and rate-limit rejections never reach metrics or the error log

- Status: Open
- Priority: P3
- Area: Server / hardening
- Found: 2026-11-11
- Verification: Pending (source-confirmed in the 2026-11-11 review; not executed)

## Problem and evidence

- **Key.** The limiter keys on `ConnectInfo(addr).ip()`
  (`crates/cognigraph-server/src/hardening.rs:266-289`). The production
  baseline in `docs/operations/configuration.md` asks for both "TLS terminates
  at your reverse proxy" and the rate limit on. Behind a proxy all users share
  one bucket: one client exhausts it for everyone, or the limit is set so high
  that it throttles nobody. [CG-76](CG-76.md) mentions this in passing.
- **Observability.** `TimeoutLayer` and `rate_limit` are layered outside
  `record_metrics` (`main.rs:691-715`). A 408 drops the metrics future
  mid-flight: `requests_total` is incremented but no status class, duration or
  error event is recorded. 429 responses are never seen.
- **Error bodies.** `to_bytes(body, 64 * 1024).await.unwrap_or_default()`
  (`hardening.rs:184-187`) replaces any 4xx or 5xx body over 64 KiB with an
  empty one. A Lua script that raises a 100 KB error gets a 500 with an empty
  body and an empty logged message.

## Acceptance

- [ ] Either a trusted-proxy setting resolves the client address, or the documentation states the limiter is per peer and is not a per-client control behind a proxy.
- [ ] 408 and 429 responses are counted and logged.
- [ ] Oversized error bodies reach the client unchanged, with only the logged message truncated; tests cover each point.
