# CG-102: Embedding providers cannot tell queries from documents

- Status: Open
- Priority: P3
- Area: Embeddings / providers
- Found: 2026-09-23
- Verification: Pending (source-confirmed; symptom measured in CG-98)
- Scheduling: Design direction; measure before changing any provider default

## Problem and evidence

`EmbeddingProvider::embed(&self, texts: &[&str])` in
`crates/cognigraph-embeddings/src/lib.rs` has no notion of whether a text is
a search query or a stored document. The OpenAI, Gemini and Ollama providers
therefore send every text the same way. Several current models are trained
for asymmetric retrieval:

- Gemini embedding models accept a task type (retrieval query versus
  retrieval document).
- The Qwen3-Embedding model card asks for a one-sentence instruction on
  queries only, and states that omitting it costs "approximately 1% to 5%"
  of retrieval performance.

The [CG-98](CG-98.md) benchmark measured Qwen3-Embedding 8B through Ollama
at MRR@10 0.526 for English query-to-chunk retrieval, against 0.848 for
Gemini on the same inputs. Its query-to-side-view leg, where the query and
the side-view question have the same shape, lifted it to 0.725. The gap is
larger than the model card's figure, so the cause is not isolated. Other
candidates are Ollama's 4-bit quantization and runtime.

## Acceptance

- [ ] The provider interface can mark a text as query or document, and each
      provider maps that to its own mechanism (task type, instruction
      prefix, or nothing).
- [ ] The CG-98 harness re-runs Gemini and Qwen3-Embedding with the hint on
      the frozen inputs and reports paired differences against the
      2026-09-23 results.
- [ ] Stored vectors stay valid, or the change states which collections
      must be re-embedded.
