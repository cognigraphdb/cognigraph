# CG-149: Embedding providers match vectors to inputs by arrival order and accept any vector shape

- Status: Open
- Priority: P2
- Area: Embeddings / provider responses
- Found: 2026-11-11
- Verification: Pending (source-confirmed in the 2026-11-11 review; not executed)

## Problem and evidence

`EmbeddingData` in `crates/cognigraph-embeddings/src/openai.rs:49-52`
deserializes only `embedding`. The comment says "OpenAI returns embeddings
sorted by index, but let's be safe", but the code checks only the count
(`:107-120`); the `index` field is ignored. The OAuth provider is the same,
and no provider (`ollama.rs:87-97`, `gemini.rs:141-151`) checks that vectors
are non-empty or of equal length. The crate has no unit test for any embedding
response path, only ignored live tests, although
`completion/request_tests.rs` shows the local-stub pattern.

Failure cases:

- An OpenAI-compatible gateway returns `data` out of order, which the `index`
  field exists to allow. `POST /api/documents/embed` zips the wrong vector
  onto each document and commits atomically, with no error.
- A provider answers 200 with `embedding: []` or another dimension. The value
  is stored on documents, and on the query path it is written to the embedding
  cache, permanently with the persistent backend ([CG-180](CG-180.md)).
  In sidecar mode it then breaks vector search for the collection
  ([CG-119](CG-119.md)).

This matters more for the sidecar endpoints in [CG-103](CG-103.md).

## Acceptance

- [ ] Providers place vectors by `index` and reject duplicate, missing or out-of-range indexes.
- [ ] Empty vectors, non-uniform lengths within a response and a mismatch with the known dimension are errors.
- [ ] Stub-server unit tests cover reordered, short, duplicate-index and empty-vector responses for each wired provider.
