## Problem and evidence

Side views are generated question–answer pairs per document, embedded and
stored in the write-protected `side_views` collection as a retrieval aid
(`crates/cognigraph-construct/src/sideviews.rs`,
`crates/cognigraph-server/src/routes/sideviews.rs`,
[decision](../decisions/decision_sideviews_provider_and_benchmark.md)). They are
listed in `GENERATED_COLLECTIONS` (`crates/cognigraph-server/src/system_collections.rs`)
and deliberately excluded from promotion, attestation and materialization.

The Semantic Neurons paper (rev2, §8.2) names side views as a fourth proposal
source: a Q&A pair that keeps surfacing knowledge the graph lacks is a gap
detector, and feeding that signal into the proposal queue is safe because
proposals are inert until authorized. The paper states this is "a design
direction the architecture licenses, not a measured result".

Source review at 2.7.15 confirms nothing implements it. `POST /api/construct/propose`
(`crates/cognigraph-server/src/routes/construct/proposal.rs`,
`crates/cognigraph-construct/src/propose.rs`) accepts gaps only as explicit
`A --REL--> B` lines or from a live `/evaluate` run. No code path reads
`side_views`, correlates a side-view hit with the absence of a matching fact
edge, or emits a proposal from it. `rg -n "side_views" crates/cognigraph-construct/src`
returns only the generation contract.

This is a capability gap confirmed from documentation and source, not a
reproduced defect. Recording it here so the design direction is tracked rather
than remembered.

## Scope and boundaries

- Side views must remain quarantined: the new path may only *propose* neurons
  (status `proposed`), never write a fact, alias or ontology change.
- The signal is retrieval-side (which side-view questions answer user queries
  while the graph trace contributes nothing for the same entities), so the
  detector needs a query log or an explicit evaluation input; decide which
  before implementing.
- Independent of [CG-89](CG-89.md) and [CG-90](CG-90.md).

## Acceptance

- [x] A documented input (evaluation spec, query sample, or explicit side-view
      selection) produces gap candidates from side-view hits that have no
      corresponding fact edge for the same `space_id` and endpoints.
- [x] Candidates flow into the existing `/propose` path and are stored with
      `status: proposed`, `proposed_by` naming the side-view source, and the

## Resolution

Resolved 2026-09-23 in v2.7.37 under the
[side-view gap detector decision](../decisions/decision_sideview_gap_detector.md)
([change record](../changelog/2026-09-23-sideview-gap-detector.md)).

- `cognigraph-construct` has a read-only detector,
  `sideviews::gaps::detect_sideview_gaps`. It pairs ontology entities that a
  side view names together, keeps a pair only when exactly one relation rule
  joins the two entities and no fact edge of the space connects them in
  either direction, and aggregates support by distinct side views.
- `POST /api/construct/propose` takes an optional `side_views` selection
  (`collection`, `documents`, `min_support`, `max_candidates`, `dry_run`). A
  dry run reports candidates and skips without a provider. Otherwise the
  candidates become the gaps of the existing proposal path, and stored
  proposals add `proposed_from: "side_views"` and `side_view_source`.
- Rules in a space type name entity instances, so the detector matches rule
  endpoints by entity name, not by entity type.
- The measured run on a public kit needs model calls and review. Following
  the owner's "build now, measure later" choice it is tracked as
  [CG-97](CG-97.md).
